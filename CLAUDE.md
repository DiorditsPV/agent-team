# agent-team — бриф для агентов

Инструмент `team`: поднимает набор агентов Claude Code по описанным ролям для любого проекта. Спецификация — `docs/SPEC.md`; при расхождении кода и спецификации правится то, что устарело, и обе части приводятся в согласие.

## Цель

- Пользователь общается с одной сессией — менеджером. Остальные роли работают в своих окнах tmux, живут независимо от менеджера; пользователь может подключиться к tmux и увидеть всех.
- Инструмент не знает о проекте. Роли, общие правила и шаблоны лежат в `<проект>/agents/` (формат — `docs/SPEC.md`, заготовка — `src/agent_team/scaffold/`, библиотека общих ролей — `roles/`: роль проекта наследует общую полем `extends`, а не копирует её). В коде инструмента нет названий конкретных проектов и трекеров и конкретных команд тестов.
- Подход взят у Gas Town: идентичность роли отдельно от сессии, состояние вне агента (трекер и git), менеджер назначает задачи, слияние и надзор — отдельные функции. Стек Gas Town (Beads, Dolt, Deacon/Dogs) не берётся.

## Что строим

CLI `team`: `init`, `check`, `up`, `spawn <роль>`, `status`, `roles [--library]`, `role new|set <роль>` (в том числе `--extends`), `addr <роль>`, `peek <роль>`, `attach [роль]`, `handoff <роль>`, `handoffs`, `restart <роль>`, `send <роль> --paste`, `events`, `log`, `task <агент>`, `reap`, `set idle_stop_minutes`, `down [роль]`, `--version`; флаги и действие каждой — таблица «Команды» в `docs/SPEC.md`. Раскладка: одна tmux-сессия `team-<project>`; роли — панелями одного окна (`layout: panes`, менеджер слева) или окном на роль (`layout: windows`, менеджер — первое окно). Запуск роли: worktree → сборка инструкции (тело роли + includes) → окно tmux → `claude` с `--append-system-prompt-file`, `--session-id`, ограниченным списком `--allowedTools`; поля роли `mcp`, `plugins`, `settings`, `chrome`, `env` и `context` (слои `defaults` → общая роль → роль проекта) ограничивают MCP, плагины и окно автосжатия. `status` отдаёт размер контекста и признаки сброса, `reap` останавливает простаивающих агентов `start: on_demand`.

Десктоп-приложение AgentTeam для macOS — в `app/` (Swift 6, SwiftUI, пакет SwiftPM). Это клиент `team` и tmux: состояние команды оно берёт из `team … --json`, меняет командами `team` и пишет только менеджеру. Граница с CLI — в `docs/SPEC.md`, раздел «Десктоп-приложение»; устройство и нагрузка — `docs/app.md`.

## Правила разработки

- Python 3.10+, зависимости — только PyYAML (формат ролей) и стандартная библиотека; tmux и `claude` вызываются подпроцессами.
- Права ролей — всегда ограниченный список инструментов (`--allowedTools`); `--dangerously-skip-permissions` не использовать и не предлагать.
- Инструмент не хранит и не раздаёт задачи, не сливает ветки, не ходит в сеть. Правило распространяется и на приложение.
- Приложение: только системные фреймворки macOS, без внешних пакетов (в `app/Package.swift` нет `dependencies`) и без сети. Логику `team` оно не повторяет: недостающие данные добавляются в JSON-контракт CLI.
- Состояние истины — tmux; `.team/state.json` в репозитории проекта — кеш, `status` сверяет с действительностью. `.team/` не коммитится.
- Тесты: `uv run pytest`; у приложения — `cd app && swift test`. Всё, что вызывает `claude`, подменяется переменной `TEAM_CLAUDE_BIN` (в тестах — `cat`), реальные модели в тестах не вызываются.
- Коммиты по-русски: суть изменения и причина; без строк об авторстве.
- Ветки ведутся по git flow «feature → dev → main»:
  - `main` — выпущенное. В него вливается только `dev`, по слову владельца, fast-forward (`git merge --ff-only dev`), затем полный прогон тестов.
  - `dev` — линия сведения и проверки; сборка для владельца собирается из неё. В `dev` вливает только менеджер: принятую фичу через `git merge --no-ff feature/…`, затем полный прогон тестов на чистой копии `dev`.
  - Задача ведётся в своей ветке от свежего `dev`, в worktree роли: `git switch -c feature/<ID>-<кратко> dev`. Роль коммитит только в неё и в отчёте называет ветку и коммит. Ветки `team/<роль>` — домашние ветки worktree, работа в них не ведётся.
  - Фича отстала от `dev` или конфликтует с ним — роль вливает `dev` в фичу (`git merge dev`) и решает конфликты там. В `dev` конфликты не решаются, история `dev` и `main` не переписывается.
  - Срочное исправление выпущенного — ветка `hotfix/<ID>-<кратко>` от `main`; она вливается в `main` по слову владельца и сразу в `dev`.
  - Влитую фичу менеджер удаляет (`git branch -d`).
  - Полный прогон тестов — `uv run pytest` и `cd app && swift test`.
- Документы, которые агенты генерируют (отчёты, разборы), складываются вне репозитория.

## Порядок работы

Новая команда или изменение поведения проходит четыре шага:

1. Риск, который зависит от поведения живого `claude` или tmux («Открытые вопросы» в `docs/SPEC.md`), сначала проверяется на одной роли; результат записывается в спецификацию.
2. Код меняется вместе с тестом.
3. Пробный запуск на реальном проекте — без выкладки и без записи в боевые данные.
4. README, руководство `docs/agent-guide.md`, спецификация, описание приложения `docs/app.md` и скилл `/a-team` приводятся к сделанному.

## Что не делать

- Не вшивать в код правила конкретного проекта.
- Не ставить инструмент глобально (`uv tool install`) без запроса: запуск из репозитория через `uv run team`.
- Не запускать агентов на боевых проектах без просьбы пользователя.
