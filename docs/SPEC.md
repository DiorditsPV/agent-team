# agent-team: спецификация

Статус: реализованы все команды из таблицы «Команды»; связь и запуск ролей проверены на живом `claude` (см. «Результаты проверки»). Нерешённое — в «Открытых вопросах».

## Зачем

Инструмент поднимает набор агентов Claude Code по описанным ролям для любого проекта. Пользователь общается с одной сессией — менеджером. Остальные роли работают в своих сессиях рядом, живут независимо от менеджера, и пользователь может подключиться к tmux и увидеть всех.

Подход взят у Gas Town (Стив Йегге) и сведён к минимуму: от него берутся принципы, а не его стек (Beads, Dolt, иерархия Deacon/Dogs).

## Принципы

1. **Идентичность отдельно от сессии.** У роли постоянное имя, зона и инструкция. Сессия одноразовая: упала или переполнила контекст — роль поднимается заново под тем же именем.
2. **Состояние вне агента.** Задачи, статусы и результаты лежат в трекере проекта и в git, а не в контексте агента. Любую сессию можно пересоздать.
3. **Задачи назначает менеджер.** Исполнитель не выбирает работу сам, пока менеджер не включил такой режим.
4. **Надзор и слияние — отдельные функции.** Исполнитель не следит за собой и не сливает в основную ветку.
5. **Явная передача.** Перед пересозданием сессии роль заполняет файл передачи (`team handoff`); менеджер передаёт путь к нему новой сессии, и та начинает с него, с ветки и с трекера.
6. **Инструмент не знает о проекте.** Всё проектное (зоны, правила безопасности, трекер) живёт в ролях и общих правилах проекта.

## Состав

- Инструмент `team` (CLI) — этот репозиторий.
- Каталог `agents/` в каждом проекте — описание команды (формат ниже).
- tmux — среда, где живут сессии.
- Claude Code (`claude`) — исполнитель каждой роли.
- Десктоп-приложение AgentTeam для macOS (`app/`) — необязательное окно над `team` и tmux (см. «Десктоп-приложение»).

## Формат проекта

```
<проект>/agents/
  team.yaml            состав команды
  roles/<роль>.md      frontmatter + инструкция
  shared/*.md          общие правила, подключаемые ролям
  templates/*.md       шаблоны сообщений (выдача задачи)
```

Рядом с описанием команда держит рабочие файлы в каталоге `.team/` в home (см. ниже). Каталог не коммитится:

```
<home>/.team/
  state.json           кеш агентов: {"роль#n": {session_id, launch_session_id, started, cwd}}; `session_id` — текущая сессия агента, `launch_session_id` появляется при первой смене сессии и хранит сессию запуска
  build/<роль>.txt     собранная инструкция роли
  events.jsonl         журнал событий, по объекту JSON на строку (см. «Журнал событий»)
  handoffs/<ts>-<роль#n>.md   файлы передачи (см. «Передача»)
  build/<агент>-settings.json   файл `--settings` агента: хуки, строка состояния, запрет фона, поля `plugins` и `settings`
  build/<агент>-mcp.json        файл `--mcp-config` агента, права 0600; есть, только если задано поле `mcp`
  asks/<агент>/        открытые вопросы агента (см. `question` в `status --json`)
  statusline.json      последний JSON строки состояния с лимитами подписки (см. «Лимиты подписки»)
```

Ключ `state.json` без номера (`worker`) читается как `worker#1`; при следующей записи он сохраняется как `worker#1`.

### team.yaml

| Поле            | Значение                                                                                                               |
|-----------------|------------------------------------------------------------------------------------------------------------------------|
| `project`       | имя проекта (входит в имя tmux-сессии)                                                                                 |
| `repo`          | необязательно: основной репозиторий; задаёт home (см. ниже), по умолчанию home — корень                                |
| `tracker` | трекер проекта для людей и приложения: строка-подпись (`Linear DEMO`) или словарь с полями на выбор проекта (`{kind: linear, project: DEMO}`); выводится в `status --json`, роли его не получают, инструмент в трекер не ходит |
| `layout`        | раскладка tmux: `windows` (по умолчанию) или `panes`, см. «Раскладка tmux»                                             |
| `test_command`  | команда тестов                                                                                                         |
| `worktree_root` | где создаются worktree ролей; относительный путь считается от home                                                     |
| `manager`       | роль менеджера                                                                                                         |
| `roles`         | список ролей с полем `start`: `manual` / `on_demand` / `always` / `per_task` / `proposed`                              |
| `idle_stop_minutes` | необязательно: целое число минут больше нуля или `off`; через столько минут простоя `team reap` останавливает агентов роли со `start: on_demand` (см. «Автоостановка»). Без ключа (или с пустым значением) порог 15 минут; `off` выключает автоостановку |
| `defaults` | необязательно: поля запуска `claude`, общие для всех ролей: `mcp`, `plugins`, `settings`, `chrome`, `env`, `context` (см. «Запуск роли: MCP, плагины, настройки»). Другой ключ — ошибка |
| `mcp_servers` | необязательно: определения MCP-серверов проекта, словарь `имя: описание сервера` (описание — как в `.mcp.json`). Роль подключает сервер по имени полем `mcp` |

**home** — одна опорная точка команды: `repo` из `team.yaml`, если задан, иначе корень (каталог с `agents/`). В home запускается менеджер, лежит `.team/`, от него считаются `worktree_root`, `worktree.repo` и относительная команда тестов. Опора нужна потому, что `agents/` версионируется: из worktree проекта `team` находит копию `agents/`, и без заданного `repo` менеджер и `.team/` раздвоились бы. Проект из нескольких репозиториев с корнем без git `repo` не задаёт: home — корень, у каждой роли с worktree свой `worktree.repo`.

### Роль (roles/<роль>.md)

Frontmatter:

| Поле           | Значение                                                                                                                                 |
|----------------|------------------------------------------------------------------------------------------------------------------------------------------|
| `role`         | имя роли; совпадает с именем файла и записью в `team.yaml`                                                                               |
| `title`        | имя сессии Claude (`--name`)                                                                                                             |
| `kind`         | `manager` / `executor` / `reviewer` / `watcher`; инструмент различает только `manager` — ему дополняется инструкция и разрешается `team`; другое значение `team check` отмечает предупреждением |
| `status`       | `active` / `draft` / `proposed`; на `draft` `team check` предупреждает                                                                   |
| `description`  | одна строка о роли, в кавычках                                                                                                           |
| `model`        | модель Claude (`--model`); `inherit` или пусто — модель по умолчанию                                                                     |
| `worktree`     | `{repo, dir, branch}` или `null`; `repo` — необязательный путь от home к репозиторию, от которого создаётся worktree (по умолчанию home) |
| `zone`         | файлы и каталоги роли; `team check` предупреждает, если строка записана у двух ролей. Попадает в инструкцию разделом «Зона». Не наследуется: берётся только из файла проекта |
| `tracker_zone` | метка зоны роли в трекере; попадает в инструкцию разделом «Зона». Не наследуется: берётся только из файла проекта |
| `includes`     | файлы общих правил, которые приклеиваются к инструкции; ищутся в `agents/shared/`, затем в `shared/` библиотеки (см. ниже)               |
| `allow`        | инструменты сверх набора по умолчанию (см. «Права»)                                                                                      |
| `add_dirs`     | дополнительные каталоги, доступные роли (`--add-dir`)                                                                                    |
| `extends`      | имя общей роли из библиотеки, которую роль наследует (см. «Наследование общей роли»); без поля роль целиком описана своим файлом         |
| `exclude` | только у наследующей роли: `{includes, allow, add_dirs}` — элементы общей роли, которые проект убирает (см. «Наследование общей роли») |
| `mcp` | список имён MCP-серверов, которые видит роль; `[]` — ни одного; без поля — MCP остаются как у владельца (см. «Запуск роли: MCP, плагины, настройки») |
| `plugins` | `{off: [...]}` — выключить перечисленные плагины или `{only: [...]}` — оставить только перечисленные |
| `settings` | настройки Claude Code, которые добавляются к `--settings` роли (зарезервированные ключи игнорируются) |
| `chrome` | `false` запускает роль с `--no-chrome`; `true` ничего не добавляет |
| `env` | переменные окружения панели, словарь `ИМЯ: значение` |
| `context` | пороги размера контекста `{soft, warn, hard}` в токенах (см. «Размер контекста и сброс»); по умолчанию `250000 / 400000 / 500000` |

Тело — инструкция агенту. Сборка инструкции: тело роли, затем раздел «Зона», затем файлы из `includes`, затем описание команд `team` у менеджера. У наследующей роли перед телом стоит тело общей роли. Frontmatter в инструкцию не попадает, кроме полей `zone` и `tracker_zone`: из них собирается раздел «## Зона»:

- `zone` непуст — строка «Твоя зона: `a/`, `b`.»;
- `tracker_zone` непуст — строка «Метка твоей зоны в трекере: «X».»;
- `zone` пуст, а `kind` не `manager` — строка «Зона в роли не задана: что править, называет задача менеджера (поле «Файлы»).»;
- у менеджера раздел есть, только если задано хотя бы одно из полей.

Зону поэтому в теле не повторяют.

`includes` любой роли разрешаются по одному правилу. Файл сначала ищется в `agents/shared/` проекта, затем в `shared/` библиотеки. Файл проекта имеет приоритет: проект заменяет общее правило библиотеки, положив в `agents/shared/` файл с тем же именем. Если файла нет ни там, ни там, роль не собирается: «подключённого файла нет». Шаблоны `agents/templates/` берутся только из проекта: в библиотеке их нет.

### Библиотека общих ролей

Библиотека — готовые роли и общие правила, которые поставляются вместе с инструментом. Её исходник — каталог `roles/` этого репозитория: роли в корне, общие правила в `roles/shared/`. Ролью библиотеки считается каждый `*.md` в корне, кроме `README.md`.

При сборке пакета `roles/` кладётся внутрь пакета как `agent_team/library`, и `team` ищет библиотеку от установленного пакета, а не от пути к репозиторию. Поэтому библиотека находится и при обычной, не editable, установке. Если каталога `agent_team/library` нет (запуск из исходников, editable-установка), `team` берёт `roles/` в корне репозитория.

Роль проекта бывает двух видов:

- **собственная** — файл без `extends`, описывает роль целиком;
- **наследующая** — файл с `extends: <общая роль>`: берёт тело и поля общей роли из библиотеки и дописывает к ним уточнения проекта.

Копировать общую роль в проект не нужно. Копия перестаёт получать правки библиотеки и со временем расходится с ней. Поэтому `team check` предупреждает о файле, который назван как роль библиотеки (`manager.md`, `developer.md`), но не задаёт `extends`.

### Наследование общей роли

Наследующая роль — тонкий файл: поле `extends`, поля, которые в проекте свои, и тело с уточнениями проекта.

```markdown
---
role: developer
extends: developer
worktree: {dir: developer, branch: team/developer}
zone: [api/]
---
Команда тестов: `pytest`.
```

Инструкция наследующей роли собирается в таком порядке:

1. Тело общей роли.
2. Заголовок `## Уточнения проекта` и тело файла проекта. Если тело пустое, заголовка нет.
3. Раздел «## Зона» из `zone` и `tracker_zone` (правила — в «Сборке инструкции»).
4. Файлы из `includes`.
5. Описание команд `team`, если `kind` роли — `manager`.

Тело общей роли входит в инструкцию дословно, вместе с заполнителями `<…>` (`<команда тестов>`, `<трекер>`). Проект не вычёркивает строки общей роли. Значения заполнителей и правила, которые в проекте другие, пишутся в теле файла проекта.

Поля frontmatter делятся на три группы:

| Поля                                              | Правило                                                                                                    |
|---------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| `model`, `title`, `kind`, `description`, `status` | из файла проекта, если заданы и не пусты; иначе из общей роли                                              |
| `allow`, `includes`, `add_dirs` | объединяются: сначала элементы общей роли, кроме исключённых в `exclude`, затем проекта, повторы убраны |
| `zone`, `worktree`, `tracker_zone`                | только из файла проекта; значения общей роли не берутся                                                    |
| `mcp`, `plugins`, `settings`, `chrome`, `env`, `context` | собираются слоями `defaults` → общая роль → роль проекта; правило слоёв — в «Запуск роли: MCP, плагины, настройки» |

Поле `exclude` убирает элементы общей роли из трёх объединяемых списков. Пример: проект без трекера не подключает общее правило работы с трекером:

```yaml
exclude:
  includes: [tracker-cycle.md]
```

- `exclude` касается только элементов общей роли. Элемент, который проект сам вписал в свой список, остаётся, даже если он же есть в `exclude`.
- Ключи — только `includes`, `allow`, `add_dirs`, значения — списки строк. Другая форма (не словарь, другой ключ, значение не список или список со словарями и списками) — ошибка: роль не собирается.
- Если в общей роли нет исключаемого элемента, `team check` предупреждает: `exclude <поле>: <элемент>` — исключать нечего.
- У роли без `extends` поле `exclude` ничего не делает, и `team check` предупреждает об этом.

Остальные поля общей роли не переносятся. Наследующая роль без своего `worktree` работает без worktree, в home, как менеджер. Поэтому тонкий файл роли, которая правит файлы, задаёт `worktree` и `zone` сам.

Ограничения `extends`:

- База — роль библиотеки без собственного `extends`: наследование идёт на один уровень. Роль проекта базой быть не может.
- Значение — имя роли библиотеки: строчные латинские буквы, цифры, `-` и `_`, с буквы. Пути вида `../x` и `a/b` отклоняются.
- Имя файла роли проекта может отличаться от базы: `reviewer2.md` с `extends: reviewer` — второй ревьюер.

Если базы нет в библиотеке, база сама наследует или имя некорректно, роль не собирается: `team check` сообщает ошибку, запуск роли завершается ошибкой. Файл без `extends` собирается как собственная роль.

## Среда выполнения

### Агент: роль и номер

Агент — запущенная сессия роли. Его имя — `роль#n`: у одной роли может работать несколько агентов, например `developer#1` и `developer#2` над разными задачами. Номер нужен, чтобы адресовать каждого агента отдельно.

- `team spawn <роль>` поднимает агента с наименьшим свободным номером. Номер свободен, если у него нет живой панели; панель завершившейся сессии номер не занимает и при запуске заменяется. `team spawn <роль>#<n>` поднимает агента с этим номером.
- Агент №1 работает в worktree роли: каталог `<worktree_root>/<dir>`, ветка `branch`. Агент №n>1 получает свой worktree: каталог `<worktree_root>/<dir>-<n>`, ветка `<branch>-<n>`. Так два агента одной роли не правят один рабочий каталог.
- Команды `addr`, `peek`, `send`, `handoff`, `restart`, `down` и `attach` принимают `роль#n`. Имя без номера означает №1: `team peek developer` и `team peek developer#1` — одно и то же.
- `team up` поднимает №1 менеджера и ролей со `start: always`.

### Раскладка tmux

Раскладка выбирается полем `layout` в `team.yaml`: `windows` (по умолчанию — окно на роль) или `panes` (все роли панелями одного окна `team`: менеджер слева на половину ширины, остальные справа, у каждой панели в рамке имя агента). Роль всегда адресуется по id панели, поэтому команды работают одинаково в обеих раскладках. Время «тихо» в `status` берётся из окна, а не панели (у tmux нет счётчика по панели), в раскладке `panes` оно общее.

- Одна tmux-сессия на проект: `team-<project>`.
- В раскладке `windows` окно 0 — менеджер, затем по окну на агента; имя окна — `<роль>-<n>` (`manager-1`, `developer-2`). В раскладке `panes` у панели в рамке — `роль#n`.
- Панель агента помечена опцией tmux `@team_role` со значением `роль#n`; по ней `team` находит агентов. Метка без номера читается как №1.
- Пользователь делает `team attach` и переключается между окнами; общается только с окном менеджера.

### Запуск роли

Для роли с worktree:
1. Создать worktree агента и ветку, если их нет, — от `worktree.repo` роли (по умолчанию home). Если в этом репозитории нет ни одного коммита, запуск завершается ошибкой с кодом 1 и ничего не создаётся: ни worktree, ни ветки, ни панели. Ветка от пустого HEAD вышла бы без общей истории с основной, и работу роли нельзя было бы слить fast-forward. Сообщение называет репозиторий и предлагает первый коммит. Уже существующий каталог worktree не проверяется. Каталог и ветка зависят от номера агента (см. «Агент: роль и номер»).
2. Собрать инструкцию в `.team/build/<роль>.txt` (в home; `.team/` не коммитится).
3. Создать окно tmux с рабочим каталогом = worktree и запустить в нём `claude` с параметрами: имя сессии из `title` (`--name`), инструкция через `--append-system-prompt-file`, `--session-id` (или `--resume` при продолжении), права через `--allowedTools`, `--model` из `model`, `--add-dir` из `add_dirs`. Режим разрешений не передаётся: роль наследует режим по умолчанию из настроек владельца. Жёсткий режим перекрыл бы его, и роль вставала бы на вопросах, пока у панели никого нет. Дополнительно `team` передаёт `--settings .team/build/<агент>-settings.json` (хуки, строка состояния, запрет фона и поля роли `plugins` и `settings`), а при заданных полях роли — `--strict-mcp-config --mcp-config .team/build/<агент>-mcp.json` и `--no-chrome` (см. «Запуск роли: MCP, плагины, настройки»). В окружение агента передаются `TEAM_ROLE` (имя роли), `TEAM_AGENT` (`роль#n`), `TEAM_PROJECT` и `TEAM_REPO` (home); `CLAUDE_CODE_AUTO_COMPACT_WINDOW` из порога `context.hard` (см. «Размер контекста и сброс»); `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` и `CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF=1` (роль не уходит в фон, см. «Проверка роли»); переменные из поля роли `env`.
4. Записать в `.team/state.json` под ключом `роль#n`: id сессии Claude, время запуска, рабочий каталог.
5. Записать в журнал событий событие `spawn` (при `team restart` — `restart`).

Менеджер запускается так же, но без worktree, в home, и его инструкция дополняется описанием команд `team` (`status [--json]`, `spawn`, `log`, `events --json`, `addr`, `send --paste`, `peek`, `handoff`, `handoffs --json`, `roles [--json] [--library]`, `role new` и `role set` с `--extends`, `restart`, `down`), правилом адресации `роль#n`, правилом писать ролям SendMessage на адрес и правилом проверять готовность передачи по файлу (`sections` в `handoffs --json`), а не по выводу панели.

### Запуск роли: MCP, плагины, настройки

Роль без настройки запускается с теми MCP-серверами, плагинами и коннекторами, которые включены у владельца. Все они добавляют в стартовый контекст описания инструментов и скиллов, хотя роль ими не пользуется: в проекте-образце роль стартовала с 73–76 тыс. токенов, из них около 46 тыс. занимали неиспользуемые MCP, скиллы плагинов и коннекторы. Поля `mcp`, `plugins`, `settings`, `chrome`, `env` и `context` позволяют проекту оставить роли только нужное. Без этих полей запуск не меняется.

Поля задаются в трёх местах, слои применяются по порядку:

1. блок `defaults` в `team.yaml` — для всех ролей;
2. общая роль библиотеки, если роль её наследует;
3. роль проекта.

Правила слоёв:

- `mcp` и `chrome` заменяются целиком: последний слой, где поле задано, побеждает. Так роль проекта может сузить список серверов, заданный в `defaults`.
- `plugins`, `settings`, `env` и `context` перекрываются по ключам: ключ последнего слоя заменяет ключ предыдущего, остальные ключи остаются. У `plugins` ключи — `off` и `only`, у `context` — `soft`, `warn`, `hard`.

Пример: все роли без Chrome и с одним MCP-сервером, у ревьюера сервера нет:

```yaml
# team.yaml
defaults:
  chrome: false
  mcp: [linear]
mcp_servers:
  linear: {type: http, url: "https://mcp.linear.app/mcp"}
```

```yaml
# roles/reviewer.md, frontmatter
mcp: []
```

Что делает каждое поле:

- **`mcp`** — список имён серверов. `team` находит определение каждого имени и записывает перечисленные серверы в `.team/build/<агент>-mcp.json`, затем запускает роль с `--strict-mcp-config --mcp-config <файл>`: роль видит только эти серверы, без коннекторов и MCP из плагинов. Файл создаётся с правами `0600`, потому что в определениях бывают токены. `mcp: []` запускает роль без MCP. Если поле нигде не задано, MCP остаются как у владельца.
  - Имя ищется по порядку: `mcp_servers` в `team.yaml`; `~/.claude.json`, раздел проекта (home или корень); `~/.claude.json`, верхний уровень; `.mcp.json` в home или корне. Побеждает первое найденное. При `CLAUDE_CONFIG_DIR` файл `.claude.json` берётся из этого каталога.
  - Неизвестное имя — ошибка с перечнем известных имён. Значения из настроек владельца (токены, заголовки) `team` не печатает: наружу выходят только имена.
- **`plugins`** — `{off: [имена]}` выключает перечисленные плагины, `{only: [имена]}` оставляет только перечисленные: остальные плагины из `enabledPlugins` в `settings.json` владельца выключаются. Результат попадает в `enabledPlugins` файла `--settings`.
- **`settings`** — настройки Claude Code, которые добавляются в тот же файл `--settings`. Ключи, которые ставит сам `team` или которые задают режим разрешений, игнорируются: `hooks`, `disableAgentView`, `statusLine`, `enabledPlugins` (плагины — полем `plugins`), `permissions`, `defaultMode`, `permissionMode`, `allowedTools`, `disallowedTools`, `additionalDirectories`, `skipDangerousModePermissionPrompt`, `disableBypassPermissionsMode`. Права ролей остаются ограниченным списком инструментов (см. «Права»).
- **`claudeMdExcludes`** — ключ `settings`, который `team` заполняет сам для роли, чей worktree лежит внутри репозитория (например, `worktree_root: .claude/worktrees`):
  - Причина: Claude Code поднимается от рабочего каталога вверх и подгружает бриф каждого каталога. Без исключений роль получила бы бриф основного каталога поверх своего, в том числе личный `CLAUDE.local.md` менеджера.
  - Что делает `team`: для каждого каталога от корня репозитория до родителя worktree добавляет в `claudeMdExcludes` абсолютные пути `CLAUDE.md`, `CLAUDE.local.md` и `.claude/CLAUDE.md`. Собственный бриф worktree остаётся.
  - Бриф выше корня репозитория роль читает как прежде. Worktree вне репозитория и роль без worktree — запуск без изменений.
  - Ключ не зарезервирован: значения из поля `settings` роли идут первыми, пути `team` дописываются без повторов.
- **`chrome`** — `false` добавляет `--no-chrome`.
- **`env`** — переменные окружения панели. Имя — `[A-Z_][A-Z0-9_]*`; значение — строка, число или булево (`true`/`false`). Переменные, которые ставит `team` (`TEAM_*`, `CLAUDE_CODE_DISABLE_AGENT_VIEW`, `CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`), проект не перекрывает.
- **`context`** — пороги размера контекста (см. «Размер контекста и сброс»).

Настройки владельца (`~/.claude.json`, `~/.claude/settings.json`) `team` только читает.

`team check` проверяет эти поля для каждой роли (правило `запуск <роль>`):

- ошибка: неизвестное имя в `mcp`; неверная форма поля (`chrome` не булево, `plugins` не `off`/`only`, `env` с недопустимым именем или значением, `context` не из трёх ключей); пороги `context` вне правил (ниже);
- предупреждение: ключ `settings`, который игнорируется; переменная `env`, которую ставит `team`;
- предупреждение: пустой `mcp` у роли `executor` или `manager`, в `includes` которой есть правило про трекер (`tracker-cycle.md` или `reporting.md`): такая роль не достанет задачу через MCP.

`team roles --json` выводит собранные поля роли (см. «roles --json»): для `mcp` — имена серверов, определения не выводятся.

### Проверка роли

Разговор агента может уйти из процесса, который запустил `team`, в фоновую задачу Claude Code. У фоновой задачи нет промпта роли, поэтому агент продолжает работать без инструкции. Условия, проверенные на `claude` 2.1.292:

- Стрелка влево в пустой строке ввода и команда `/background` переносят разговор в фон сразу, без подтверждения. Задачу ведёт отдельный процесс с новым id сессии.
- Задаче передаются `--settings`, `--allowed-tools`, `--model` и режим разрешений, но не `--append-system-prompt-file` и не `--name`.
- Задача переживает закрытие панели. Сигнал SIGTERM по её pid завершает её; отдельной команды остановить одну задачу у `claude` нет.

`team` закрывает этот путь и проверяет, что он закрыт:

- При запуске роли `team` ставит `disableAgentView: true` в `--settings` и переменные `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` и `CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF=1`. Стрелка и `/background` перестают работать, а SendMessage продолжает доходить.
- `status --json` отдаёт в поле `role_check` итог проверки: ведёт ли разговор процесс панели с файлом роли в командной строке. Проверка нужна для ролей, запущенных раньше, и на случай, если `claude` найдёт другой путь в фон.
- Если проверка не прошла, текстовый `status` вместо состояния пишет `! в фоне`, `! чужой процесс` или `! без роли`, а под таблицей — причину и команду `team restart <агент>`.
- `team addr <агент>` отказывает такому агенту: сообщение ушло бы сессии без роли. Менеджер не получает адрес.
- `team restart <агент>` останавливает фоновую задачу по pid из записи сессии (сверив командную строку процесса) и поднимает панель заново: роль продолжает разговор той задачи, но уже с промптом роли. Сессию для продолжения `restart` определяет до закрытия панели (запись процесса панели держит ссылку на задачу), поэтому продолжается актуальный разговор, в том числе начатый после `/clear`, а не сессия запуска. Если разговор ведёт чужой процесс, не запущенный `team`, `restart` без `--fresh` отказывает и просит закрыть процесс или взять `--fresh`.
- `team reap` и признак `reset_ready` не трогают агента, у которого проверка не прошла.

### Размер контекста и сброс

Контекст роли растёт с каждым ходом, и каждый следующий ход заново обрабатывает всё накопленное. Роль, которая вошла в новую задачу с примерно 310 тыс. токенов старого контекста, платит за него в каждом ходе. Поэтому `team status` показывает размер контекста, а менеджер сбрасывает роль на границе задач. `team` сам роль не сбрасывает: он сообщает признаки, а решает менеджер.

Поле роли `context` задаёт три порога в токенах (в роли, общей роли или `defaults`; слои — как у полей запуска):

| Порог | По умолчанию | Значение |
|-------|--------------|----------|
| `soft` | 250000 | простаивающая роль выше порога должна быть сброшена на ближайшей границе задачи: `reset_due` |
| `warn` | 400000 | работающая роль выше порога должна закончить задачу и быть сброшена: `context_warning` |
| `hard` | 500000 | окно автосжатия Claude Code: `team` передаёт его переменной `CLAUDE_CODE_AUTO_COMPACT_WINDOW` |

Правила порогов: `soft < warn <= hard`; `hard` — от 100000 до 1000000 (допустимые значения переменной по бинарю `claude` 2.1.292). Нарушение — ошибка `team check`, а запуск роли отказывает.

Как `status` считает признаки:

- `ctx` — размер контекста последнего хода ассистента в транскрипте текущей сессии: `input + cache_creation + cache_read`. На ходе с advisor берётся последняя итерация типа `message`, потому что общая сводка складывает запросы исполнителя и советника. У неживого агента и до первого хода `ctx` равен `null`.
- `compactions` — число сжатий в транскрипте (записи `compact_boundary`); у неживого агента `null`.
- `reset_due` — агент простаивает (`state: "idle"`), и `ctx` выше `soft`.
- `context_warning` — агент работает (`state: "busy"`), и `ctx` выше `warn`.
- `reset_ready` — при `reset_due` показывает, можно ли сбрасывать сейчас; иначе `null`. Причины отказа — список `reset_blockers`: `worktree грязный: N файлов` (мусор окружения вроде `.DS_Store` и `__pycache__` не считается), `в панели не сессия роли`, `в панели открыт диалог`.

В текстовом `status` столбец `ctx` показывает размер в тысячах токенов (`312k`). Пометка `сброс` — пора сбрасывать; `сброс*` — пора, но `reset_blockers` не пуст (причины печатаются строкой под таблицей); `!` — работающая роль выше `warn`.

Правило менеджера (`roles/manager.md`): перед выдачей новой задачи роли проверь `reset_due`. Если он `true`, порядок такой: `team handoff <роль>` и заполненная передача, `team restart <роль> --fresh`, выдача задачи сообщением на новый адрес. Границей считается приёмка отчёта и снятие задачи; ответ посреди задачи (утверждён план, чини находки) границей не считается и сброса не требует. Если `reset_ready` равен `false`, менеджер сначала устраняет причину. `team handoff` на грязном worktree отказывает (см. «Передача»), чтобы несохранённое не потерялось после сброса.

### Лимиты подписки

Claude Code передаёт команде `statusLine` JSON сессии на stdin; в нём есть `rate_limits`: окно в 5 часов (`five_hour`) и недельный лимит (`seven_day`) — процент и время сброса. Приложению эти данные нужны для боковой панели, а отдельных запросов к API `team` не делает. Поэтому `team` оборачивает строку состояния роли: обёртка кладёт последний JSON с лимитами в `.team/statusline.json` проекта (через временный файл и rename), а затем запускает прежнюю команду `statusLine` владельца с тем же stdin и печатает её вывод. Строка выглядит так же, как без `team`.

- Прежняя команда ищется при каждом вызове в порядке старшинства настроек Claude Code: пользовательские (`$CLAUDE_CONFIG_DIR` или `~/.claude`), проекта (`.claude/settings.json`), локальные проекта (`.claude/settings.local.json`); побеждает последняя заданная. Команды нет — вывод пустой.
- JSON без лимитов файл не меняет. JSON с `rate_limits_available: false` (ключ API, Bedrock, Vertex) записывается: по нему приложение скрывает строку лимитов.
- Любая ошибка обёртки молча пропускается, код выхода 0: строка состояния не ломается из-за лимитов.
- Обёртку ставит запуск роли, поэтому у роли, запущенной раньше, лимитов нет до `team restart`.

### Права

Каждая роль получает ограниченный список инструментов. Набор по умолчанию: `Read`, `Edit`, `Write`, `Glob`, `Grep`, `Bash(git *)` и `Bash(<первое слово test_command> *)`; менеджеру добавляется `Bash(team *)`. Расширение — в поле `allow` роли: интеграции (MCP трекера), линтер, `Agent`. Инструменты из списка роль вызывает без вопроса. Что происходит с остальными, решает режим разрешений по умолчанию из настроек Claude Code владельца (`permissions.defaultMode`): инструмент режим не задаёт. Полный обход проверок (`--dangerously-skip-permissions`) инструмент не использует.

### Связь

Основной канал — встроенный обмен сообщениями Claude Code (SendMessage) на адрес сокета роли `uds:<путь>`. `team addr <роль>` находит его по записи сессии `~/.claude/sessions/<pid>.json` (pid панели, затем sessionId из `.team/state.json`). Адрес, а не имя: имена сессий неуникальны, а сообщение через сокет роль видит как письмо другой сессии с именем отправителя, а не как ввод пользователя. `team send` без `--paste` ничего не вставляет: он завершается ошибкой и называет адрес; вставка в строку ввода — только явным флагом.

Переменные родительской сессии Claude снимаются внутри панели при запуске (`sh -c` с циклом unset и `exec`), а не по списку вызывающего процесса: панель получает окружение tmux-сервера, который помнит окружение сессии, однажды его поднявшей. Иначе роль регистрируется дочерней чужой сессии и получает её имя (`nameSource: peer`).

- **Менеджер → роль:** SendMessage на адрес из `team addr <роль>`.
- **Роль → менеджер:** SendMessage менеджеру и комментарий в трекере. Менеджер при необходимости читает вывод роли командой `team peek <роль>`.
- **Запасной путь:** `team send <роль> --paste` вставляет текст в строку ввода через tmux (`load-buffer` + `paste-buffer` + Enter). Роль видит его как ввод пользователя, поэтому путь используется только когда у роли нет адреса.
- Пользователь пишет только менеджеру. Ответы ролей он видит у менеджера или в панели роли.

### Жизненный цикл

- `up` — поднять менеджера и роли со `start: always`; остальные поднимаются по требованию менеджера (`team spawn <роль>`). Для каждой поднятой роли `up` печатает то же предупреждение о недоверенном каталоге, что и `spawn`.
- `down [агент]` — закрыть панель агента или всю сессию. Корректная остановка — сначала `handoff <агент>`, затем `down`.
- `reap` — остановить простаивающих агентов `start: on_demand` по порогу `idle_stop_minutes` (см. «Автоостановка»).
- `restart <агент>` — поднять заново: продолжить сессию (`--resume <id>`) или, с `--fresh`, начать новую. С `--fresh` команда ждёт регистрации сессии (до 10 с) и печатает `адрес для SendMessage: <адрес>` и `последняя передача: <путь к файлу>` (или «файла передачи у роли нет»); менеджер отправляет новой сессии путь к файлу передачи на этот адрес. Если адрес за 10 с не появился, команда пишет, что он пока не зарегистрирован, и предлагает `team addr <агент>` позже.
- Состояние истины — сам tmux; `.team/state.json` — кеш, который `status` сверяет с действительностью.

### Автоостановка

Роль со `start: on_demand` поднимается под задачу и после неё остаётся в панели. Простаивающий агент держит контекст и место, но работу не двигает. Поэтому `team reap` останавливает таких агентов по простою. Порог задаёт ключ `idle_stop_minutes` в `team.yaml`: целое число минут больше нуля. Без ключа (или с пустым значением) порог равен 15 минутам. `off` (YAML читает его как `false`, `false` тоже годится) выключает автоостановку: `team reap` ничего не делает. Порог по умолчанию нужен потому, что без него агенты `on_demand` простаивали часами, и Claude Code сжимал их контекст без хода, тратя лимит.

`team` сам по таймеру не работает: `reap` вызывает тот, кто хочет автоостановку. Приложение вызывает его раз в минуту для каждого проекта с живой tmux-сессией команды, открыт он в приложении или нет; проект без живой сессии пропускается. Цикл стартует при запуске приложения. `team.yaml` приложение для этого не разбирает: при `off` решает сам `team reap` (см. «Десктоп-приложение»).

`team reap [--keep <агент>…] [--dry-run] [--json]` смотрит каждого живого агента и либо останавливает его, либо оставляет с причиной. Остановка делает то же, что `team down <агент>`: закрывает панель, пишет событие `down` с текстом «остановлена: простой N мин», снимает задачу и вопрос.

Агента `reap` не трогает, если верно хотя бы одно (причина попадает в вывод как `reason`):

- агент назван в `--keep` (причина «назван в --keep»);
- это менеджер («менеджер»);
- у роли `start` не `on_demand` («start: <режим>»);
- проверка роли не прошла («в панели не сессия роли», см. «Проверка роли»);
- агент ждёт ответа человека («ждёт ответа»);
- агент работает, `state: "busy"` («работает»);
- у агента есть задача: номер или название («есть задача: <название>»);
- данных о простое нет («нет данных о простое»);
- простой меньше порога («простой N мин < M»);
- в панели открыт диалог Claude Code («в панели открыт диалог»);
- в строке ввода набран текст («в строке ввода набран текст»).

Задача защищает агента потому, что отчёт и вопрос обычным текстом (не через `AskUserQuestion`) хук `team` не видит: агент выглядит простаивающим, пока менеджер не принял работу. Менеджер принимает работу и снимает задачу (`team task <агент> --clear`); тогда простой считается от более позднего из двух моментов: последнего действия агента и снятия задачи. Значение — `min(idle_s, now - task_cleared_ts)`: агент, который ждал приёмки час, после снятия задачи получает полный порог, а не выключается сразу.

Вывод:

- текст: по строке на агента `<агент>: <действие> (<причина>)`, где действие — `stopped`, `would_stop` (с `--dry-run`) или `kept`; нет живых агентов — «живых агентов нет»; при `off` — «автоостановка выключена: idle_stop_minutes: off»;
- `--json`: список `{name, idle_s, action, reason}`; при `off` — `[]`.

`--dry-run` только показывает решение и ничего не останавливает. `--keep` принимает несколько имён (роль или `роль#n`); флаг можно повторять.

Команда `team set idle_stop_minutes <N|off> [--json]` меняет порог в `team.yaml`, не трогая остальной файл: строка `idle_stop_minutes: N` заменяется на месте (комментарий в конце строки сохраняется), а если ключа нет — встаёт перед блоком `roles:`. `off` пишет в `team.yaml` строку `idle_stop_minutes: off`, ключ не убирается. Значение проверяется тем же правилом, что при загрузке `team.yaml`: не целое или не больше нуля — ошибка, файл не меняется. Строка в непонятной форме (например, значение блоком на следующих строках) — ошибка с просьбой поправить вручную. Печать: `idle_stop_minutes: N` или `idle_stop_minutes: off (выключено)`; с `--json` — `{"key": "idle_stop_minutes", "value": N}` (`null` при `off`). Пустое значение `set` не принимает. Другие ключи `set` не принимает: приложению нужно только менять автоостановку без ручной правки YAML.

### Передача

Передача — файл, в котором агент перед пересозданием сессии записывает состояние своей работы. Новая сессия читает его вместо утерянного контекста.

Перед созданием файла `team handoff` проверяет рабочий каталог агента. Если в нём есть незакоммиченные изменения (мусор окружения — `.DS_Store`, `__pycache__`, `.team`, `*.pyc`, `*.swp` — не считается; у роли без своего worktree, `worktree: null`, не считаются и неотслеживаемые каталог агентов проекта и `.claude/`, а изменения отслеживаемых файлов считаются), команда завершается с кодом 1 и называет число и первые пять путей. Причина: после сброса сессии несохранённое терялось бы из виду. Файл и событие при отказе не создаются. Роль коммитит или откладывает правки; если сброс всё равно нужен, `team handoff <агент> --force` создаёт передачу и на грязном worktree.

1. `team handoff <агент> [--task X] [--reason "…"] [--force]` создаёт файл `.team/handoffs/<ts>-<роль#n>.md`, где `ts` — время создания в unix-секундах. Шапка файла — frontmatter: `agent`, `ts`, `task`, `reason`, `status: waiting`, `branch` (ветка рабочего каталога агента по git), `worktree` (рабочий каталог). Ниже — пять пустых разделов с подсказками в HTML-комментариях: «Сделано», «Проверено», «В работе», «Подводные камни», «Дальше».

   Повторный запрос не плодит файлы. Если последняя передача агента ещё `waiting` и все её разделы пусты (HTML-комментарии не считаются), команда пишет в тот же файл: обновляет в шапке `branch` и `worktree`, а `task` и `reason` — если они заданы флагами; имя файла и `ts` остаются прежними. Если последняя передача заполнена хотя бы в одном разделе или помечена `used`, создаётся новый файл.
2. Команда пишет событие `handoff` с текстом «запрос передачи: <путь>», при повторе в тот же файл — «повторный запрос передачи: <путь>», и готовит запрос агенту. В запросе назван путь к файлу:

   > Подготовь передачу: заполни файл <путь> (разделы «Сделано», «Проверено», «В работе», «Подводные камни», «Дальше»; комментарии-подсказки удали) и продублируй итог комментарием в задаче трекера. Незакоммиченное зафиксируй или перечисли. После этого ничего не делай.

   Без флагов команда печатает адрес агента и этот текст: менеджер отправляет его SendMessage. С `--paste` запрос вставляется в строку ввода агента. Если адрес не найден, команда завершается с кодом 1, но файл и событие к этому моменту уже созданы. Повторный `team handoff <агент> --paste` после такой ошибки пишет в тот же файл.
3. Агент заполняет разделы. Готовность передачи проверяется по файлу, а не по выводу панели агента: в `team handoffs --json` у передачи непустые поля `sections`.
4. `team restart <агент> --fresh` помечает последнюю по времени передачу этого агента `status: used`, добавляет строку `used_at: <время>` и поднимает новую сессию. Новая сессия сама файл не читает: путь к нему ей передаёт менеджер.

### Журнал событий

Журнал — файл `.team/events.jsonl`: по одному событию на строку, без перезаписи. Он нужен, чтобы восстановить ход работы команды, не читая панели.

Событие — объект `{ts, type, agent, text, task}`: время в unix-секундах, тип, имя агента, текст и задача трекера (или `null`). У событий, которые пишет `team task`, есть ещё ключ `title`: название задачи или `null`, если задача снята (см. «Название задачи агента»). Типы:

- `spawn`, `restart`, `down`, `handoff` пишет сам `team` при соответствующих командах. `team down` без аргумента пишет `down` на каждую панель агента в сессии, включая завершившиеся;
- `task` пишет `team task`, а также `team down` и `team restart --fresh`, когда снимают задачу;
- `task`, `report`, `commit`, `waiting`, `owner` пишет менеджер или скрипт командой `team log <тип> <агент> <текст> [--task X]`. Событие `task` от `team log` ключа `title` не имеет.

В `team log` имя роли без номера приводится к `роль#1`. Имя, которое не совпадает ни с одной ролью (например, `owner`), записывается как есть. Тип вне списка — ошибка. Строка журнала, которая не разбирается как JSON, при чтении пропускается.

### Название задачи агента

Название — короткая подпись для владельца: над чем сейчас работает агент. Номер задачи в трекере владельцу ничего не говорит, поэтому название описывает работу словами. Его ставит менеджер, когда выдаёт задачу, и снимает, когда принимает работу.

- `team task <агент> "<название>" [--id N]` ставит название: пишет событие `task` с `text` и `title`, равными названию, и `task`, равным `--id` (без `--id` — `null`). Пробелы в названии сводятся к одному.
- `team task <агент> --clear` снимает задачу: пишет событие `task` с `task: null`, `title: null` и текстом «задача снята: по просьбе». Если задачи нет, событие не пишется.
- `team task <агент>` без названия печатает текущую задачу: `<агент>: <название> [<номер>]`, `<агент>: (без названия) [<номер>]`, если у задачи есть только номер, или `<агент>: задачи нет`.

Текущая задача агента — последнее событие `task` этого агента в журнале. Событие от `team log task … --task X` даёт номер без названия.

Название проверяется до записи:

- длина после сведения пробелов — от 8 до 48 знаков;
- не голый номер задачи (`#12`, `DEMO-12`): номер передаётся через `--id`;
- без путей (`/a`, `~/a`, `./a`, `a/b/c`, обратная косая черта) и имён файлов с расширением (`app.py`);
- без обратных кавычек;
- в одну строку.

Если название не прошло проверку, команда завершается с кодом 1, печатает в stderr «название задачи не принято:» и список нарушений с тем, что поправить; событие не пишется. Ошибкой завершаются и `--clear` вместе с названием или `--id`, `--id` без названия, агент роли, которой нет в `team.yaml`.

Задачу снимают и другие команды: `team down <агент>` и `team down` (для каждой панели) пишут событие с текстом «задача снята: роль остановлена», `team restart <агент> --fresh` — «задача снята: новая сессия». `team restart` с продолжением прежней сессии задачу не снимает.

### Правка ролей из командной строки

`team role set` и `team role new` меняют описание команды без ручной правки файлов. Обе команды правят текст по строкам, а не перезаписывают YAML целиком, поэтому тело роли, комментарии и остальные поля сохраняются байт в байт. Обе печатают JSON роли в формате элемента `roles --json` и принимают `--json` для единообразия с другими командами.

Ошибка любой из двух команд — код выхода 1 и текст в stderr; файлы роли и `team.yaml` при этом не меняются. Ошибки `--extends` — те же, что у поля `extends` (см. «Наследование общей роли»): общей роли нет в библиотеке, общая роль сама наследует, имя некорректно.

`team role set <роль>` правит поля существующей роли; нужен хотя бы один флаг:

- `--title`, `--model`, `--description` переписывают строку ключа во frontmatter файла роли; отсутствующий ключ добавляется перед закрывающей `---`. `--model` принимает `opus`, `sonnet` или `haiku`;
- `--start` (`manual`, `always`, `on_demand`) переписывает `start` в строке роли в `team.yaml`. Понятные формы строки: `- {role: x, start: …}`, блок `- role: x` со строкой `start:` или без неё, `- x`. Строку другой формы команда не трогает и завершается ошибкой;
- `--extends <общая роль>` записывает `extends` во frontmatter, и роль начинает наследовать общую роль. `--extends ""` удаляет ключ `extends`, и роль снова собирается как собственная. Тело файла команда не трогает: у роли, которая была собственной, всё её тело становится уточнениями проекта и идёт после тела общей роли.

`team role new <роль> --extends <общая роль>` заводит наследующую роль:

- имя роли проверяется так же, как ниже; роль с таким именем в `team.yaml` или такой файл — ошибка;
- файл `agents/roles/<роль>.md` — тонкий: frontmatter `role`, `extends`, `title`, `description` и `model`, если они заданы флагами, `zone: []`; если у общей роли есть `worktree` — свой `worktree: {dir: <роль>, branch: team/<роль>}`. Тело — HTML-комментарий о том, что писать в уточнениях проекта. `title`, `kind` и `includes` роль получает от общей роли;
- в конец списка `roles` в `team.yaml` добавляется `- {role: <роль>, start: <start>}`, по умолчанию `start: manual`;
- `--title` не обязателен.

`team role new <роль> --title <…>` без `--extends` заводит собственную роль-исполнителя; `--title` здесь обязателен:

- имя роли — строчные латинские буквы, цифры, `-` и `_`, с буквы (`^[a-z][a-z0-9_-]*$`); роль с таким именем в `team.yaml` или такой файл — ошибка;
- файл `agents/roles/<роль>.md` получает frontmatter `role`, `title`, `kind: executor`, `status: active`, `description`, `model` (если задан), `worktree: {dir: <роль>, branch: team/<роль>}`, `zone: []` и `includes` первой роли с `kind: executor` по порядку `team.yaml`; тело — одна строка-заготовка;
- в конец списка `roles` в `team.yaml` добавляется `- {role: <роль>, start: <start>}`; `--start` принимает те же значения, что у `role set`, по умолчанию `on_demand`; если роли с `kind: executor` нет, `includes` пустой;
- worktree не создаётся: его создаёт первый `team spawn`.

## Машиночитаемый вывод

Флаг `--json` есть у `status`, `roles`, `check`, `events`, `handoffs`, `reap` и `set`; `role set` и `role new` печатают JSON всегда. Вывод — JSON в UTF-8 с отступом 2 в stdout, код выхода 0. Время везде — unix-секунды, пути — абсолютные.

Ошибки в JSON не приходят. Команда печатает в stderr строку `team: <сообщение>` и завершается с кодом 1. Ошибка разбора аргументов (например, `--model gpt`) завершается с кодом 2 и справкой `argparse`. Исключение — `check --json`: он печатает JSON и при найденных ошибках, а код выхода 1 сообщает, что ошибки есть.

Объект команды:

| `tracker` | `tracker` из `team.yaml`: строка остаётся строкой, словарь — объектом с теми же ключами (ключи приводятся к строкам, значения, которых нет в JSON, например даты, — к строкам); нет поля или пустое значение — `null` |
| `agents`        | список агентов (ниже)                     |

Список `agents` идёт по порядку ролей в `team.yaml`, внутри роли — по номеру. В него попадает каждый агент, у которого есть панель в сессии, живая или завершившаяся. Если у роли нет ни одной панели, в списке одна запись №1 с `alive: false`. Остановленный `team down` агент №n>1 из списка пропадает.

| Поле            | Значение                                                                                                           |
|-----------------|--------------------------------------------------------------------------------------------------------------------|
| `name`          | `роль#n`                                                                                                           |
| `role`, `n`     | имя роли и номер агента                                                                                            |
| `title`, `kind` | из frontmatter роли; у наследующей роли — после наследования                                                       |
| `model`         | `model` роли; без значения — `"inherit"`                                                                           |
| `alive`         | панель есть и её процесс работает                                                                                  |
| `pane_id`       | id панели tmux (`%N`) или `null`, если панели нет; у завершившейся панели id есть, `alive: false`                  |
| `session_id` | id текущей сессии Claude. У живого агента это `sessionId` записи `~/.claude/sessions/<pid панели>.json` (при `parkedJobId` — записи задачи), если у этой сессии есть транскрипт: `/clear` начинает новую сессию и не оставляет в старом транскрипте отметки `continued-in`. Если записи нет, панель завершилась или транскрипта нет, берётся последняя сессия цепочки `continued-in` от сессии в `state.json`. Сменившаяся сессия записывается в `state.json`, поэтому `status`, `ctx`, `restart` и приложение видят актуальный разговор. `null`, если сессии нет |
| `launch_session_id` | id сессии, с которой `team` запустил агента: при первой смене `session_id` `state.json` сохраняет её в этом поле; до смены равен `session_id`; `null`, если сессии нет |
| `transcript` | путь к файлу транскрипта текущей сессии или `null` |
| `cwd`           | рабочий каталог из `state.json`; если агент не запускался — каталог по плану (worktree или home)                   |
| `branch`        | текущая ветка git в `cwd`, если каталог есть; иначе ветка по плану; `null`, если её нет                            |
| `started`       | время запуска; у неживого агента `null`                                                                            |
| `state` | состояние по записи сессии Claude Code: `busy` (идёт ход), `idle` (ход окончен, ждёт ввода), `waiting` (ждёт ответа человека); `null`, если записи нет или значение неизвестно (например, `claude` ещё не открыл сессию) |
| `idle_s` | секунды простоя; у неживого `null`. Есть запись сессии: при `busy` — `0`, при `idle` и `waiting` — секунды с последней смены `state`. Записи нет: секунды с последнего вывода в окне tmux (в раскладке `panes` окно общее, и время общее для всех) |
| `waiting_human` | агент стоит на вопросе о доверии к каталогу, запросе права или вопросе агента (ниже); у неживого `false`            |
| `waiting_reason` | на чём стоит агент: `"trust"` — вопрос о доверии к каталогу, `"prompt"` — запрос права или вопрос агента; `null`, если агент не ждёт или неживой. `waiting_human` равно `true` ровно тогда, когда `waiting_reason` не `null` |
| `addr`          | адрес `uds:…` для SendMessage или `null`, если агент неживой или сокет не найден                                   |
| `task` | номер задачи из последнего события `task` этого агента (`--id` у `team task`, `--task` у `team log`); `null`, если номера нет, событий нет или задача снята |
| `task_title` | название задачи из того же события (`title`); `null`, если названия нет или задача снята |
| `task_ts` | время того же события; `null`, если событий нет или задача снята |
| `task_cleared_ts` | время последнего снятия задачи (событие `task` с `title: null`); `null`, если задачу не снимали. От него `reap` считает простой (см. «Автоостановка») |

| `role_check` | итог проверки роли или `null`, если панели и сессии нет (ниже) |
| `ctx`, `compactions`, `ctx_limits`, `reset_due`, `reset_ready`, `reset_blockers`, `context_warning` | размер контекста и признаки сброса (см. «Размер контекста и сброс»); `ctx_limits` — `{soft, warn, hard}` роли |
| `dirty`         | незакоммиченные пути в `cwd` по `git status --porcelain`, список строк; `null`, если каталога нет или это не git   |

`question` — вопрос, который агент задал инструментом `AskUserQuestion`. Claude Code обрезает форму такого вопроса в узкой панели и пишет одиночный вопрос без выбора, поэтому `team` ставит роли хук на `AskUserQuestion` (в `--settings` роли, до и после вызова), и хук записывает вопрос в `.team/asks/<агент>/`. `question` — `{id, ts, questions}`, где `questions` — список `{question, header, multiSelect, options}`, а `options` — список `{label, description[, preview]}`. Поле есть, пока вопрос открыт в текущей сессии: ответ в транскрипте, перезапуск агента или другая сессия его закрывают. Если известное `state` — не `waiting`, формы на экране нет и `question` равен `null`.

`role_check` — `{ok, reason, pid, pane_pid, job_id, session_id}`. `ok: true` — разговор ведёт процесс панели с файлом роли; `ok: false` — нет, и `reason` — `background` (фоновая задача), `other_process` (чужой процесс) или `no_role_prompt` (процесс панели без файла роли); `ok: null` — данных нет (сессия ещё регистрируется или в панели не `claude`). См. «Проверка роли».

`branch` и `dirty` `team` читает командой `git --no-optional-locks`. Без этого флага `git status` берёт `index.lock` в worktree агента, и `git commit` агента, совпавший по времени с опросом, падает.

Источник признака — запись сессии Claude Code. Если запись есть и её состояние `waiting`, ставится `waiting_reason: "prompt"`. Если записи нет (на вопросе о доверии `claude` ещё не открыл сессию), `team` смотрит последние 15 строк панели и ищет в них один из признаков ниже.

Вопрос о доверии к каталогу (`waiting_reason: "trust"`; проверяется раньше остальных):

- «Is this a project you created or one you trust»;
- «Yes, I trust this folder».

Остальные признаки дают `waiting_reason: "prompt"`.

Вопрос о праве:

- «Do you want to» с одним из продолжений `proceed`, `make this edit`, `create`, `allow`, `run`, `overwrite`;
- «Would you like to proceed»;
- строка выбора `❯ 1. Yes`.

Форма вопроса агента:

- «Enter to select … Esc to cancel» в одной строке;
- «Review your answers».

Одно «Esc to cancel» ожиданием не считается: оно стоит и в меню владельца, например `/rewind` («Enter to continue · Esc to cancel»), а там агент не ждёт решения.

Проверено на живых экранах `claude` 2.1.295: запрос права, форма вопроса агента и меню `/rewind`; на `claude` 2.1.292 — вопрос о доверии к каталогу (экраны узкой и широкой панели лежат в `tests/fixtures/live-trust-narrow.txt` и `live-trust-wide.txt`, тесты — `tests/test_trust.py`). Экраны лежат в фикстурах приложения (`app/Tests/AgentTeamCoreTests/Fixtures/live-*.txt`), тесты — `tests/test_waiting_human.py`. Строка ввода — набранный текст, `@`, слеш-команда, многострочный ввод — ожиданием не считается.

Не проверено на живом `claude`:

- экран «Review your answers»: строка взята по предположению, тест подставляет собственный текст.

Текстовый `team status` показывает ожидание в столбце «состояние»: «ждёт: доверие» при `waiting_reason: "trust"`, «ждёт ответа» при `"prompt"`. Под таблицей для каждого агента на вопросе о доверии печатается строка `<агент>: стоит на вопросе о доверии к каталогу <cwd> — ответ человека: team attach <агент>`.

### check --json

Объект `{passed, issues}`. `issues` — все проверки по порядку, включая успешные: `{level, title, detail}`, где `level` — `error`, `warn` или `ok`, `title` — что проверялось (`tmux`, `роль executor`, `зоны`), `detail` — сообщение. `passed` — число проверок с `level: ok`. Код выхода 1, если есть хотя бы один `error`.

Список событий журнала (см. «Журнал событий»), новые первыми; события с одинаковым `ts` — в обратном порядке записи. `--since <ts>` оставляет события с `ts` не раньше заданного, включительно. `--limit <n>` оставляет первые `n` после сортировки.

## Доверие к каталогу

Claude Code хранит ответ на вопрос о доверии в глобальном конфиге: `$CLAUDE_CONFIG_DIR/.claude.json`, а без `CLAUDE_CONFIG_DIR` — `~/.claude.json`. Каталог доверен, если в `projects[<путь>]` стоит `hasTrustDialogAccepted: true`. Доверие распространяется на вложенные каталоги: worktree под доверенным родителем вопроса не задаёт.

`team` этот файл только читает и доверие сам не ставит. Доверие — решение владельца, а файл целиком переписывают живые сессии `claude`, так что запись со стороны гонялась бы с ними.

Если каталог роли не доверен, `team` предупреждает до вопроса:

- `spawn`, `up` и `restart` после строки о запуске печатают «внимание: каталог … не доверен в Claude Code» с командой для владельца;
- `check` даёт предупреждение `доверие`, одно на каталог для доверия, со списком ролей; роли со `status: draft` пропускаются.

Если конфиг не читается или в нём нет `projects`, предупреждения нет: `team` не знает, доверен ли каталог.

В предупреждении назван один каталог, доверие к которому снимает вопрос для всех агентов роли:

- у роли с worktree — корень worktree (`worktree_root` из `team.yaml`, по умолчанию `../wt`): все worktree роли лежат под ним;
- у роли без worktree, включая менеджера, — home команды.

Владелец отвечает один раз на новой машине: `cd <каталог> && claude`, ответ «Yes, I trust this folder», затем `/exit`. Если этого не сделать, роль встаёт на вопросе, и ответ даёт человек через `team attach <агент>`.

`team` передаёт агенту `TEAM_ROLE`, `TEAM_AGENT`, `TEAM_PROJECT` и `TEAM_REPO` (см. «Запуск роли»). Сам `team` читает:

| Переменная          | Действие                                                                                                                                                 |
|---------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| `TEAM_TMUX_SOCKET`  | имя сокета tmux (`tmux -L <имя>`) для всех команд, включая `attach`. Тесты задают свой сокет на каждый тест, чтобы не задевать живые сессии пользователя |

## Десктоп-приложение

AgentTeam — нативное приложение macOS в `app/` (Swift 6, SwiftUI, пакет SwiftPM). Оно показывает команду в одном окне: проекты из сессий tmux `team-*`, панели агентов с живым выводом, чат с менеджером, экран агента, роли (вместе с настройками `team.yaml` и результатом `team check`), передачи и журнал; в боковой панели — лимиты подписки. Устройство, обоснования и замер нагрузки — в [`app.md`](app.md) (на английском); там же требования и ограничения.

Приложение — клиент `team`, а не вторая реализация: логику инструмента оно не повторяет. Состояние команды оно берёт из `team … --json` и меняет только командами `team` и вставкой сообщения владельца в панель менеджера. Граница между ними — контракт «Машиночитаемый вывод». Данные, которых приложению не хватает, добавляются в этот контракт: так в нём появились `task`, `dirty` и `used_at`.

Что приложение читает:

- через `team`: `status --json`, `roles --json`, `handoffs --json`, `check --json`. Вызовы идут по событиям, а не по таймеру; `status` — не чаще раза в 15 с, после действия владельца — сразу. Исключение — `team reap --json`: приложение вызывает его раз в минуту для каждого проекта с живой tmux-сессией команды, открыт он в приложении или нет, без условия по разбору `team.yaml` (см. «Автоостановка»). У открытого проекта в `--keep` идут очередь и черновик менеджера; у неоткрытого `--keep` пуст, модель проекта не создаётся. Проект без живой сессии пропускается; цикл стартует при запуске приложения;
- проверка роли: приложение читает `role_check` из `status --json`; если в панели не сессия роли, оно показывает плашку с кнопкой «Восстановить роль» (`team restart <агент>`) и не пишет в панель менеджера, пока роль не восстановлена. Перед каждой записью в панель менеджера приложение подтверждает роль свежим `team status --json`;
- из tmux: одно соединение control mode (`tmux -C attach-session`) на всё приложение — уведомления, списки сессий и панелей, захват панелей;
- файлы: хвост журнала `.team/events.jsonl`, `.team/statusline.json` (лимиты подписки для боковой панели; запасной источник — кеш `/usage` в `~/.claude.json`), `agents/team.yaml` (имя проекта, роль менеджера, настройки на экране «Роли» и `idle_stop_minutes`), транскрипт менеджера `~/.claude/projects/<slug>/<session_id>.jsonl`. Изменения в `.team/` и `agents/` (FSEvents) — сигнал перечитать данные через `team`;
- git — только со старым `team` без `--json`: `git --no-optional-locks status --porcelain` в каталоге агента.

Что приложение пишет:

- через `team`: `spawn`, `restart [--fresh]`, `down`, `role set` (в том числе `--start`), `role new`, `reap` и `log owner` — запись сообщения владельца в журнал. `team set idle_stop_minutes <N|off> --json` — из ячейки «автоостановка» на экране «Роли» (без ключа в ней 15 с подписью «по умолчанию», при `off` — «выкл»): владелец вводит число минут, «выкл», `off` или `false` (все три записывают `off`); пустое поле записывает 15. Enter или кнопка «Записать» вызывают команду, после успеха приложение перечитывает `team.yaml`, ошибка показывается под полем. Неверный ввод (не целое число больше нуля) подсвечивается красным и в `team` не уходит;
- в tmux: сообщение владельца в панель менеджера (`load-buffer`, `paste-buffer -p`, затем `Enter`) и настройки своего клиента (`refresh-client`);
- свои настройки в user defaults и временные файлы: текст сообщения перед вставкой, скрипт `.command`, который открывает панель агента в Терминале.

Владелец пишет только менеджеру. В панель агента приложение ничего не вставляет: «Передать» на экране агента — тоже сообщение менеджеру с просьбой о передаче.

## Что инструмент не делает

Список относится и к CLI, и к приложению.

- Не хранит и не раздаёт задачи: это трекер проекта.
- Не сливает ветки: это роль менеджера.
- Не следит за зависшими задачами: это роль-дозорный (если проект её вводит).
- Не ходит в сеть и не меняет данные проектов.

## Известные ограничения

- MCP-серверы Claude Code в local scope и скиллы из `.claude/` привязаны к каталогу запуска. Исполнители в worktree вне home не видят MCP и скиллы корня. Серверы, нужные исполнителю, подключаются ему полем `mcp` и блоком `mcp_servers` (см. «Запуск роли: MCP, плагины, настройки»); скиллы из `.claude/` корня так не подключить.
- Размер контекста и признаки сброса `team` только сообщает. Приложение их пока не показывает; сброс ведёт менеджер.

## Результаты проверки (пробный запуск настоящего `claude` в tmux)

1. **Ввод через tmux работает.** `team send --paste` вставляет текст в окно, роль отвечает; инструкция роли (`--append-system-prompt-file`) действует.
2. **Встроенная связь работает.** Сессия в tmux появляется в `ListAgents` как «interactive» с указанием окна tmux, и ей можно писать `SendMessage`. Имя (`--name` из `title`) неуникально, поэтому менеджер пишет на адрес сокета из `team addr` (см. «Связь»).
3. **Переменные родителя надо сбрасывать.** Запущенная из сессии Claude роль наследует `CLAUDE_*` (сокет и токен обмена, id сессии, каталог задачи) и сливается с родителем: то же имя, тот же сокет. Поэтому команда запуска внутри панели снимает все `CLAUDE_*`, кроме `CLAUDE_CONFIG_DIR` (`build.UNSET_CLAUDE_VARS`, см. «Связь»).
4. **Запрос доверия к каталогу.** В каталоге, где `claude` ещё не запускался (новый worktree), он спрашивает «Is this a project you created or one you trust?»; курсор по умолчанию стоит на «No, exit». Роль встаёт на этом вопросе. Инструмент намеренно не нажимает «да»: доверие к каталогу — решение человека. Вопрос виден в `team peek <агент>`; человек отвечает через `team attach <агент>`. `team` узнаёт вопрос по тексту экрана (проверено на `claude` 2.1.292): `status --json` ставит `waiting_human: true` и `waiting_reason: "trust"`, текстовый `team status` пишет «ждёт: доверие». Заранее, до вопроса, о нём предупреждают `spawn`, `up`, `restart` и `check` (см. «Доверие к каталогу»). Приложение ищет этот вопрос отдельными маркерами.
5. **Признак «закончила ход».** В выводе роли после ответа видна строка вида «done HH:MM»; для надёжного определения занятости полагаться на неё нельзя без проверки на разных версиях.

## Открытые вопросы

1. **Занята ли роль.** Состояние `busy` / `idle` / `waiting` `team` берёт из записи сессии Claude Code (`state`). Пока записи нет (на вопросе о доверии `claude` ещё не открыл сессию), остаётся только время последнего вывода в окне (`idle_s`), а в раскладке `panes` оно общее для всех ролей. Отчёт и вопрос агента обычным текстом, без `AskUserQuestion`, запись сессии от простоя не отличает: поэтому `reap` не останавливает агента с задачей.
2. **Запросы подтверждения.** Если роль упрётся в запрос права вне списка и режим разрешений владельца требует подтверждения, она встанет. `status --json` отмечает такие панели полем `waiting_human` по тексту последних 15 строк. Шаблоны проверены на `claude` 2.1.295; открыто, держатся ли они на других версиях.
3. **Рост контекста.** `team` показывает размер контекста и пороги сброса (см. «Размер контекста и сброс»), а сброс ведёт менеджер на границе задачи.
4. **Перенос ведущей сессии.** Текущая интерактивная сессия менеджера не может стать окном tmux; менеджер в tmux — новая сессия с чистым контекстом, состояние берётся из трекера и ветвей.
