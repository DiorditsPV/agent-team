# agent-team: спецификация

Статус: реализованы все команды из таблицы «Команды»; связь и запуск ролей проверены на живом `claude` (см. «Результаты проверки»). Нерешённое — в «Открытых вопросах».

## Зачем

Инструмент поднимает набор агентов Claude Code по описанным ролям для любого проекта. Пользователь общается с одной сессией — менеджером. Остальные роли работают в своих сессиях рядом, живут независимо от менеджера, и пользователь может подключиться к tmux и увидеть всех.

Подход взят у Gas Town (Стив Йегге) и сведён к минимуму: от него берутся принципы, а не его стек (Beads, Dolt, иерархия Deacon/Dogs).

## Принципы

1. **Идентичность отдельно от сессии.** У роли постоянное имя, зона и инструкция. Сессия одноразовая: упала или переполнила контекст — роль поднимается заново под тем же именем.
2. **Состояние вне агента.** Задачи, статусы и результаты лежат в трекере проекта и в git, а не в контексте агента. Любую сессию можно пересоздать.
3. **Задачи назначает менеджер.** Исполнитель не выбирает работу сам, пока менеджер не включил такой режим.
4. **Надзор и слияние — отдельные функции.** Исполнитель не следит за собой и не сливает в основную ветку.
5. **Явная передача.** При пересоздании сессии контекст передаётся по шаблону (`handoff`).
6. **Инструмент не знает о проекте.** Всё проектное (зоны, правила безопасности, трекер) живёт в ролях и общих правилах проекта.

## Состав

- Инструмент `team` (CLI) — этот репозиторий.
- Каталог `agents/` в каждом проекте — описание команды (формат ниже).
- tmux — среда, где живут сессии.
- Claude Code (`claude`) — исполнитель каждой роли.

## Формат проекта

```
<проект>/agents/
  team.yaml            состав команды
  roles/<роль>.md      frontmatter + инструкция
  shared/*.md          общие правила, подключаемые ролям
  templates/*.md       шаблоны сообщений (выдача задачи, передача)
```

### team.yaml

| Поле            | Значение                                                                                  |
|-----------------|-------------------------------------------------------------------------------------------|
| `project`       | имя проекта (входит в имя tmux-сессии)                                                    |
| `repo`          | необязательно: основной репозиторий; задаёт home (см. ниже), по умолчанию home — корень   |
| `tracker`       | вид и проект трекера (для справки ролям; инструмент в трекер не ходит)                    |
| `layout`        | раскладка tmux: `windows` (по умолчанию) или `panes`, см. «Раскладка tmux»                |
| `test_command`  | команда тестов                                                                            |
| `worktree_root` | где создаются worktree ролей; относительный путь считается от home                        |
| `manager`       | роль менеджера                                                                            |
| `roles`         | список ролей с полем `start`: `manual` / `on_demand` / `always` / `per_task` / `proposed` |

**home** — одна опорная точка команды: `repo` из `team.yaml`, если задан, иначе корень (каталог с `agents/`). В home запускается менеджер, лежит `.team/`, от него считаются `worktree_root`, `worktree.repo` и относительная команда тестов. Опора нужна потому, что `agents/` версионируется: из worktree проекта `team` находит копию `agents/`, и без заданного `repo` менеджер и `.team/` раздвоились бы. Проект из нескольких репозиториев с корнем без git `repo` не задаёт: home — корень, у каждой роли с worktree свой `worktree.repo`.

### Роль (roles/<роль>.md)

Frontmatter:

| Поле           | Значение                                                                                                                       |
|----------------|--------------------------------------------------------------------------------------------------------------------------------|
| `role`         | имя роли; совпадает с именем файла и записью в `team.yaml`                                                                     |
| `title`        | имя сессии Claude (`--name`)                                                                                                   |
| `kind`         | `manager` / `executor` / `reviewer` / `watcher`; инструмент различает только `manager` — ему дополняется инструкция и разрешается `team` |
| `status`       | `active` / `draft` / `proposed`; на `draft` `team check` предупреждает                                                          |
| `description`  | одна строка о роли, в кавычках                                                                                                 |
| `model`        | модель Claude (`--model`); `inherit` или пусто — модель по умолчанию                                                           |
| `worktree`     | `{repo, dir, branch}` или `null`; `repo` — необязательный путь от home к репозиторию, от которого создаётся worktree (по умолчанию home) |
| `zone`         | файлы и каталоги роли; `team check` предупреждает, если строка записана у двух ролей. В инструкцию агента не попадает               |
| `tracker_zone` | метка зоны роли в трекере; для справки, инструмент её не читает                                                                |
| `includes`     | файлы из `agents/shared/`, которые приклеиваются к инструкции                                                                  |
| `allow`        | инструменты сверх набора по умолчанию (см. «Права»)                                                                            |
| `add_dirs`     | дополнительные каталоги, доступные роли (`--add-dir`)                                                                          |

Тело — инструкция агенту. Сборка инструкции: тело роли + файлы из `includes` (+ описание команд `team` у менеджера). Frontmatter в инструкцию не попадает, поэтому то, что агент должен знать о своей зоне, пишется в теле.

## Среда выполнения

### Раскладка tmux

Раскладка выбирается полем `layout` в `team.yaml`: `windows` (по умолчанию — окно на роль) или `panes` (все роли панелями одного окна `team`: менеджер слева на половину ширины, остальные справа, у каждой панели в рамке имя роли). Роль всегда адресуется по id панели, поэтому команды работают одинаково в обеих раскладках. Время «тихо» в `status` берётся из окна, а не панели (у tmux нет счётчика по панели), в раскладке `panes` оно общее.

- Одна tmux-сессия на проект: `team-<project>`.
- В раскладке `windows` окно 0 — менеджер, затем по окну на роль, имя окна = имя роли.
- Пользователь делает `team attach` и переключается между окнами; общается только с окном менеджера.

### Запуск роли

Для роли с worktree:
1. Создать worktree и ветку, если их нет, — от `worktree.repo` роли (по умолчанию home).
2. Собрать инструкцию в `.team/build/<роль>.txt` (в проекте, в `.gitignore`).
3. Создать окно tmux с рабочим каталогом = worktree и запустить в нём `claude` с параметрами: имя сессии из `title` (`--name`), инструкция через `--append-system-prompt-file`, `--session-id` (или `--resume` при продолжении), права через `--allowedTools` и `--permission-mode acceptEdits`, `--model` из `model`, `--add-dir` из `add_dirs`. В окружение роли передаются `TEAM_ROLE`, `TEAM_PROJECT` и `TEAM_REPO` (home).
4. Записать в `.team/state.json` под именем роли: id сессии Claude, время запуска, рабочий каталог.

Менеджер запускается так же, но без worktree, в home, и его инструкция дополняется описанием команд `team` (`status`, `spawn`, `addr`, `send --paste`, `peek`, `handoff`, `restart`, `down`) и правилом писать ролям SendMessage на адрес.

### Права

Каждая роль получает ограниченный список инструментов. Набор по умолчанию: `Read`, `Edit`, `Write`, `Glob`, `Grep`, `Bash(git *)` и `Bash(<первое слово test_command> *)`; менеджеру добавляется `Bash(team *)`. Расширение — в поле `allow` роли: интеграции (MCP трекера), линтер, `Agent`. Полный обход проверок (`--dangerously-skip-permissions`) инструмент не использует.

### Связь

Основной канал — встроенный обмен сообщениями Claude Code (SendMessage) на адрес сокета роли `uds:<путь>`. `team addr <роль>` находит его по записи сессии `~/.claude/sessions/<pid>.json` (pid панели, затем sessionId из `.team/state.json`). Адрес, а не имя: имена сессий неуникальны, а сообщение через сокет роль видит как письмо другой сессии с именем отправителя, а не как ввод пользователя. `team send` без `--paste` ничего не вставляет и печатает адрес; вставка в строку ввода — только явным флагом.

Переменные родительской сессии Claude снимаются внутри панели при запуске (`sh -c` с циклом unset и `exec`), а не по списку вызывающего процесса: панель получает окружение tmux-сервера, который помнит окружение сессии, однажды его поднявшей. Иначе роль регистрируется дочерней чужой сессии и получает её имя (`nameSource: peer`).

- **Менеджер → роль:** SendMessage на адрес из `team addr <роль>`.
- **Роль → менеджер:** SendMessage менеджеру и комментарий в трекере. Менеджер при необходимости читает вывод роли командой `team peek <роль>`.
- **Запасной путь:** `team send <роль> --paste` вставляет текст в строку ввода через tmux (`load-buffer` + `paste-buffer` + Enter). Роль видит его как ввод пользователя, поэтому путь используется только когда у роли нет адреса.
- Пользователь пишет только менеджеру. Ответы ролей он видит у менеджера или в панели роли.

### Жизненный цикл

- `up` — поднять менеджера и роли со `start: always`; остальные поднимаются по требованию менеджера (`team spawn <роль>`).
- `down [роль]` — закрыть панель роли или всю сессию. Корректная остановка — сначала `handoff <роль>`, затем `down`.
- `restart <роль>` — поднять заново: продолжить сессию (`--resume <id>`) или начать новую с передачей по шаблону.
- Состояние истины — сам tmux; `.team/state.json` — кеш, который `status` сверяет с действительностью.

### Команды

| Команда                            | Действие                                                                                      |
|------------------------------------|-----------------------------------------------------------------------------------------------|
| `team`                             | напечатать поток работы                                                                       |
| `team init`                        | создать `agents/` из заготовки в текущем каталоге; если `team.yaml` есть — ошибка, ничего не перезаписывается |
| `team check`                       | проверить описание без запуска: tmux и `claude` в `PATH`, разбор ролей и `includes`, `kind` менеджера, повтор `worktree.dir`, worktree от не-git каталога, черновики, пересечение зон; код выхода 1 при ошибках |
| `team up [--resume]`               | поднять tmux-сессию проекта, менеджера и роли `always`; `--resume` — продолжить прежние сессии  |
| `team spawn <роль> [--resume]`     | поднять роль                                                                                  |
| `team status`                      | роли, живы ли, давно ли было действие, адрес для SendMessage                                  |
| `team addr <роль>`                 | адрес роли `uds:…` для SendMessage                                                            |
| `team peek <роль> [строк]`         | показать последние строки окна роли (по умолчанию 40)                                         |
| `team attach [роль]`               | подключиться к tmux (к панели роли, по умолчанию менеджера)                                   |
| `team handoff <роль> [--paste]`    | напечатать адрес и текст запроса передачи; с `--paste` — вставить запрос в строку ввода        |
| `team restart <роль> [--fresh]`    | пересоздать сессию роли: продолжить прежнюю (`--resume <id>`) или, с `--fresh`, начать новую   |
| `team send <роль> --paste <текст>` | вставить текст в строку ввода роли; без `--paste` — ошибка с адресом для SendMessage          |
| `team down [роль]`                 | остановить роль или всю команду                                                               |

## Что инструмент не делает

- Не хранит и не раздаёт задачи: это трекер проекта.
- Не сливает ветки: это роль менеджера.
- Не следит за зависшими задачами: это роль-дозорный (если проект её вводит).
- Не ходит в сеть и не меняет данные проектов.

## Известные ограничения

- MCP-серверы Claude Code в local scope и скиллы из `.claude/` привязаны к каталогу запуска. Исполнители в worktree вне home не видят MCP и скиллы корня: интеграции, нужные исполнителю, подключаются ему отдельно, работа с трекером остаётся за менеджером.

## Результаты проверки (пробный запуск настоящего `claude` в tmux)

1. **Ввод через tmux работает.** `team send --paste` вставляет текст в окно, роль отвечает; инструкция роли (`--append-system-prompt-file`) действует.
2. **Встроенная связь работает.** Сессия в tmux появляется в `ListAgents` как «interactive» с указанием окна tmux, и ей можно писать `SendMessage`. Имя (`--name` из `title`) неуникально, поэтому менеджер пишет на адрес сокета из `team addr` (см. «Связь»).
3. **Переменные родителя надо сбрасывать.** Запущенная из сессии Claude роль наследует `CLAUDE_*` (сокет и токен обмена, id сессии, каталог задачи) и сливается с родителем: то же имя, тот же сокет. Поэтому команда запуска внутри панели снимает все `CLAUDE_*`, кроме `CLAUDE_CONFIG_DIR` (`build.UNSET_CLAUDE_VARS`, см. «Связь»).
4. **Запрос доверия к каталогу.** В каталоге, где `claude` ещё не запускался (новый worktree), он спрашивает «доверяете ли папке». Роль встаёт на этом вопросе. Инструмент намеренно не нажимает «да»: доверие к каталогу — решение человека. Вопрос виден в `team peek <роль>`; человек отвечает через `team attach <роль>`. Отдельного признака в `team status` нет.
5. **Признак «закончила ход».** В выводе роли после ответа видна строка вида «done HH:MM»; для надёжного определения занятости полагаться на неё нельзя без проверки на разных версиях.

## Открытые вопросы

1. **Занята ли роль.** Надёжно определить «занят / ждёт» из tmux трудно; начальный вариант — по времени последнего изменения вывода и маркеру в инструкции роли («пишу ГОТОВО в конце хода»). Нужна проверка на практике.
2. **Запросы подтверждения.** Если роль упрётся в запрос права вне списка, она встанет. `team status` должен показывать такие окна, а `peek` — вопрос.
3. **Рост контекста.** Долгоживущая роль рано или поздно переполняется; политика пересоздания по порогу или по команде менеджера.
4. **Перенос ведущей сессии.** Текущая интерактивная сессия менеджера не может стать окном tmux; менеджер в tmux — новая сессия с чистым контекстом, состояние берётся из трекера и ветвей.
