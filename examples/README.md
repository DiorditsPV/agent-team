# Библиотека ролей

Команда агентов Claude Code в tmux: вы говорите с одним менеджером, роли постоянны, а сессии одноразовы — состояние живёт в git и трекере, а не в контексте агента.

Этот каталог — готовые описания ролей и общих правил для такой команды. Их собрали из команд, которые работали на настоящих проектах, свели дубликаты и убрали всё проектное. Каждый файл роли можно скопировать в `agents/roles/` своего проекта без правки формата: остаётся заполнить зону, команду тестов и трекер.

Охват: что делает каждая роль, когда её поднимать и как перенести её в проект. Формат полей frontmatter и устройство инструмента здесь не повторяются — они описаны в [`docs/SPEC.md`](../docs/SPEC.md). Предполагается, что проект уже подключён к `team` (`team init`) или вы готовы это сделать.

## Роли

Роли перечислены в порядке, в котором их обычно добавляют в команду: менеджер нужен всегда, остальные — по работе. Столбец «start» — значение для `team.yaml`, с которого стоит начать.

| Роль                             | Для чего                                                                                 | kind     | start       | Когда поднимать                                                                                              |
|----------------------------------|------------------------------------------------------------------------------------------|----------|-------------|--------------------------------------------------------------------------------------------------------------|
| `manager` — менеджер             | Ведёт очередь, раздаёт задачи, принимает работу по факту, сливает по слову владельца     | manager  | `manual`    | Всегда: это ведущая сессия, с ней говорит пользователь                                                       |
| `developer` — разработчик        | Правит код и тесты своей зоны в своём worktree                                           | executor | `on_demand` | Под задачу разработки; `always`, если код идёт постоянно                                                     |
| `writer` — писатель              | Пишет документацию по коду и отчётам разработчика; проверяет инструкции свежим читателем | executor | `on_demand` | Когда задача меняет поведение, описанное в документах, или нужен документ                                    |
| `reviewer` — ревьюер             | Проверяет ветку до слияния, вердикт «принять» или «вернуть»                              | reviewer | `on_demand` | Перед каждым слиянием ветки исполнителя                                                                      |
| `judge` — судья                  | Независимо проверяет значимую работу и ищет сценарии отказа, которых тесты не видят      | reviewer | `per_task`  | На работу, которая меняет схему или массово данные, выкладывается, меняет режим системы или заявляет прирост |
| `data` — инженер данных          | Схема, миграции, конвейеры, витрины; все массовые операции — с копией и отменой          | executor | `on_demand` | Когда в проекте есть своя база или конвейер данных                                                           |
| `optimizer` — оптимизатор        | Улучшает измеримую метрику работающей системы с замерами до и после                      | executor | `on_demand` | Когда есть метрика (скорость, нагрузка, доля отказов) и система работает под нагрузкой                       |
| `assistant` — помощник менеджера | Выясняет факты и готовит решения для менеджера; только читает                            | executor | `on_demand` | Когда менеджер тратит много времени на разбор перед решениями                                                |
| `watcher` — дозорный             | Находит зависшие задачи, простаивающие роли и неслитые ветки и сообщает менеджеру        | watcher  | `proposed`  | Когда ролей много и менеджер не успевает следить за ходом работы                                             |

Дозорный в живых командах не запускался: его роль описана, но не проверена работой, поэтому у него `status: proposed`. Остальные роли работали в настоящих проектах.

Две частые разновидности не вынесены в отдельные файлы, потому что это те же роли с другим именем:

- **Второй ревьюер** при длинной очереди на ревью — копия `reviewer.md` под именем `reviewer2.md` с `role: reviewer2` и своим `title`.
- **Исполнитель без своей зоны** («свободные руки») — копия `developer.md` под другим именем, у которой `zone` остаётся пустым, а не заполняется. Вместо строки «Твоя зона» в тело вписывается правило: файлы называет менеджер в задаче, а файл из зоны другой роли правится только с согласия её владельца, переданного через менеджера.

## Общие правила

Общие правила лежат в `shared/`. Роль подключает их полем `includes`, и инструмент приклеивает их к инструкции роли при запуске.

| Файл                    | Что задаёт                                                                                     | Кто подключает                              |
|-------------------------|------------------------------------------------------------------------------------------------|---------------------------------------------|
| `reporting.md`          | Вопросы — менеджеру, а не пользователю; формат отчёта; ожидание после отчёта                   | все роли                                    |
| `safety.md`             | Секреты, сеть, выкладка только через менеджера, общие ресурсы, безопасные команды shell, права | все роли                                    |
| `git-worktree.md`       | Свой worktree, своя зона, коммиты поимённо, слияние только у менеджера                         | менеджер и роли, которые правят файлы       |
| `tracker-cycle.md`      | Выбор задачи, статусы In Progress / Hold / Done, описание задачи                               | менеджер и исполнители                      |
| `data-reversibility.md` | Копия до массовой операции, предупреждение менеджеру, сверка счётчиков, удаление копий         | `data` и любая роль, которая трогает данные |

## Как взять роль в свой проект

1. Подключите проект, если `agents/` ещё нет:

   ```bash
   cd <проект>
   team init
   ```

   `team init` создаёт `agents/team.yaml`, заготовки ролей `manager` и `executor`, `shared/reporting.md` и шаблоны `templates/task-assignment.md` и `templates/handoff.md`. На эти шаблоны ссылаются роли библиотеки, поэтому их не удаляйте.

2. Скопируйте файлы нужных ролей в `agents/roles/`. Имя файла должно совпадать с полем `role:`. Заготовку `executor.md` от `team init` удалите или оставьте, но тогда она тоже должна быть в `team.yaml`.

   ```bash
   cp <клон agent-team>/examples/roles/{manager,developer,reviewer}.md agents/roles/
   ```

3. Скопируйте в `agents/shared/` все файлы из полей `includes` скопированных ролей. Без них `team check` сообщит об ошибке «подключённого файла нет». Файл `reporting.md` из библиотеки заменяет заготовку `team init`: он дополнен правилом, что вопросы идут менеджеру.

   ```bash
   cp <клон agent-team>/examples/shared/{safety,tracker-cycle,git-worktree,reporting}.md agents/shared/
   ```

4. Замените заполнители в угловых скобках (таблица ниже) и поля frontmatter, помеченные комментарием.

5. Впишите роли в `agents/team.yaml` и задайте команду тестов. Значения `start` описаны в [`docs/SPEC.md`](../docs/SPEC.md).

   ```yaml
   test_command: <команда тестов>
   manager: manager
   roles:
     - role: manager
       start: manual
     - role: developer
       start: on_demand
     - role: reviewer
       start: on_demand
   ```

6. Проверьте описание:

   ```bash
   team check
   ```

   Команда разбирает frontmatter каждой роли, собирает её инструкцию с `includes` и сверяет worktree и зоны между ролями. Итог — строка `роли: …; ошибок N, предупреждений M`. Поднимать команду (`team up`) можно, когда ошибок 0.

## Что заменить

Заполнители стоят в теле ролей и в общих правилах. Найти их можно поиском `<` по скопированным файлам.

| Заполнитель или поле           | Где                                    | Что вписать                                                                              |
|--------------------------------|----------------------------------------|------------------------------------------------------------------------------------------|
| `<трекер>`                     | `manager.md`, `tracker-cycle.md`       | Название трекера и проекта в нём; без трекера — удалите `tracker-cycle.md` из `includes` |
| `<команда тестов>`             | роли, которые запускают проверку       | Команда полного прогона тестов, та же, что `test_command` в `team.yaml`                  |
| `<каталоги и файлы>` и похожие | строка «Твоя зона» в теле исполнителей | Каталоги и файлы, которые правит только эта роль                                         |
| `zone`                         | frontmatter исполнителей               | Тот же список, что в строке «Твоя зона»                                                  |
| `allow`                        | frontmatter                            | Инструменты сверх набора по умолчанию: MCP трекера, линтер, проверка типов               |
| `tracker_zone`                 | frontmatter                            | Метка зоны роли в трекере                                                                |
| `<команда резервной копии>`    | `data-reversibility.md`                | Команда, которая делает копию данных и проверяет её целостность                          |
| `<что улучшаем…>`, `<период>`  | `optimizer.md`                         | Метрика роли и минимальный период между сменами настроек режима                          |

Зону приходится писать дважды. Поле `zone` во frontmatter нужно `team check`: по нему он находит файлы, записанные за двумя ролями сразу. Но в инструкцию агента frontmatter не попадает — агент видит только тело роли и подключённые правила. Поэтому зона повторяется строкой «Твоя зона» в теле.
