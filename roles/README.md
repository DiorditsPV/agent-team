# Библиотека ролей

Команда агентов Claude Code в tmux: вы говорите с одним менеджером, роли постоянны, а сессии одноразовы — состояние живёт в git и трекере, а не в контексте агента.

Этот каталог — библиотека: готовые описания ролей и общих правил для такой команды. Их собрали из команд, которые работали на настоящих проектах, свели дубликаты и убрали всё проектное. Библиотека ставится вместе с инструментом, и `team` находит её сам.

Роль из библиотеки в проект не копируют. Проект подключает её тонким файлом с полем `extends` и пишет в нём только своё: зону, worktree, команду тестов, трекер. Копия перестаёт получать правки библиотеки и со временем расходится с ней, а тонкий файл получает их при следующем запуске роли.

Охват: что делает каждая роль, когда её поднимать и как подключить её к проекту. Формат полей frontmatter, точные правила наследования и устройство инструмента здесь не повторяются — они описаны в [`docs/SPEC.md`](../docs/SPEC.md), разделы «Роль», «Библиотека общих ролей» и «Наследование общей роли». Предполагается, что проект уже подключён к `team` (`team init`) или вы готовы это сделать.

## Роли

Роли перечислены в порядке, в котором их обычно добавляют в команду: менеджер нужен всегда, остальные — по работе. Столбец «start» — значение для `team.yaml`, с которого стоит начать.

| Роль                             | Для чего                                                                                 | kind     | start       | Когда поднимать                                                                                              |
|----------------------------------|------------------------------------------------------------------------------------------|----------|-------------|--------------------------------------------------------------------------------------------------------------|
| `manager` — менеджер             | Ведёт очередь, раздаёт задачи, принимает работу по факту, сливает по слову владельца     | manager  | `manual`    | Всегда: это ведущая сессия, с ней говорит пользователь                                                       |
| `developer` — разработчик        | Правит код и тесты своей зоны в своём worktree                                           | executor | `on_demand` | Под задачу разработки; `always`, если код идёт постоянно                                                     |
| `writer` — писатель              | Пишет документацию по коду и отчётам разработчика; проверяет инструкции свежим читателем | executor | `on_demand` | Когда задача меняет поведение, описанное в документах, или нужен документ                                    |
| `reviewer` — ревьюер             | Проверяет ветку до слияния, вердикт «принять» или «вернуть»                              | reviewer | `on_demand` | Перед каждым слиянием ветки исполнителя                                                                      |
| `judge` — судья                  | Независимо проверяет значимую работу и ищет сценарии отказа, которых тесты не видят      | reviewer | `per_task`  | На работу, которая меняет схему или массово данные, выкладывается, меняет режим системы или заявляет прирост |
| `data` — инженер данных          | Схема, миграции, конвейеры, витрины; все массовые операции — с копией и отменой          | executor | `on_demand` | Когда в проекте есть своя база или конвейер данных                                                           |
| `optimizer` — оптимизатор        | Улучшает измеримую метрику работающей системы с замерами до и после                      | executor | `on_demand` | Когда есть метрика (скорость, нагрузка, доля отказов) и система работает под нагрузкой                       |
| `assistant` — помощник менеджера | Выясняет факты и готовит решения для менеджера; только читает                            | executor | `on_demand` | Когда менеджер тратит много времени на разбор перед решениями                                                |
| `watcher` — дозорный             | Находит зависшие задачи, простаивающие роли и неслитые ветки и сообщает менеджеру        | watcher  | `proposed`  | Когда ролей много и менеджер не успевает следить за ходом работы                                             |

Дозорный в живых командах не запускался: его роль описана, но не проверена работой, поэтому у него `status: proposed`. Остальные роли работали в настоящих проектах.

Две частые разновидности не вынесены в отдельные файлы, потому что это те же роли с другим именем. Имя файла роли проекта может отличаться от имени общей роли в `extends`:

- **Второй ревьюер** при длинной очереди на ревью — файл `reviewer2.md` с `role: reviewer2`, `extends: reviewer` и своим `title`: `team role new reviewer2 --extends reviewer --title "Ревьюер 2" --start on_demand`.
- **Исполнитель без своей зоны** («свободные руки») — файл под своим именем с `extends: developer`, своим `worktree` и без `zone`. Инструкция такой роли получает раздел «Зона» со строкой «Зона в роли не задана: что править, называет задача менеджера (поле «Файлы»)». Правило «файл из зоны другой роли правится только с согласия её владельца, переданного через менеджера» пишется в уточнениях проекта.

## Общие правила

Общие правила лежат в `shared/`. Роль подключает их полем `includes`, и инструмент приклеивает их к инструкции роли при запуске. Файл из `includes` инструмент ищет сначала в `agents/shared/` проекта, затем в `shared/` библиотеки, поэтому копировать общие правила в проект не нужно. Файл проекта с тем же именем заменяет библиотечный: так проект меняет общее правило под себя.

| Файл                    | Что задаёт                                                                                     | Кто подключает                              |
|-------------------------|------------------------------------------------------------------------------------------------|---------------------------------------------|
| `reporting.md`          | Вопросы — менеджеру, а не пользователю; формат отчёта; ожидание после отчёта                   | все роли                                    |
| `safety.md`             | Секреты, сеть, выкладка только через менеджера, общие ресурсы, безопасные команды shell, права | все роли                                    |
| `git-worktree.md`       | Свой worktree, своя зона, коммиты поимённо, слияние только у менеджера                         | менеджер и роли, которые правят файлы       |
| `tracker-cycle.md`      | Выбор задачи, статусы In Progress / Hold / Done, описание задачи                               | менеджер и исполнители                      |
| `reading.md`            | Экономное чтение: окна вместо файлов целиком, вывод сборки в файл, git сначала `--stat`, обзор через Explore | все роли                                    |
| `data-reversibility.md` | Копия до массовой операции, предупреждение менеджеру, сверка счётчиков, удаление копий         | `data` и любая роль, которая трогает данные |

## Роли проекта: собственные и наследующие

Роль проекта — файл `agents/roles/<роль>.md`. Она бывает двух видов:

- **наследующая** — тонкий файл с `extends: <общая роль>`. Инструкция агента собирается из тела общей роли, заголовка `## Уточнения проекта` и тела тонкого файла, затем подключаются `includes`;
- **собственная** — файл без `extends`, который описывает роль целиком. Её пишут, когда подходящей общей роли нет.

Пример тонкого файла разработчика:

```markdown
---
role: developer
extends: developer
worktree: {dir: developer, branch: team/developer}
zone: [api/]
---
Команда тестов: `pytest`.
```

Что тонкий файл получает от общей роли и что задаёт сам:

- `model`, `title`, `kind`, `description`, `status` берутся из общей роли, если тонкий файл их не задаёт;
- `includes`, `allow`, `add_dirs` складываются: сначала списки общей роли, затем проекта, повторы убраны. Элемент общей роли тонкий файл убирает полем `exclude` (пример ниже);
- `mcp`, `plugins`, `settings`, `chrome`, `env`, `context` собираются слоями: блок `defaults` в `team.yaml`, затем общая роль, затем тонкий файл. `mcp` и `chrome` заменяются целиком, остальные поля — по ключам. Так тонкий файл сужает список MCP-серверов или меняет пороги контекста (`context: {soft, warn, hard}`), не копируя поля общей роли. Правила — в `docs/SPEC.md`, раздел «Запуск роли: MCP, плагины, настройки»;
- `zone`, `worktree`, `tracker_zone` задаёт только тонкий файл. У общей роли они не наследуются, поэтому роли, которая правит файлы, нужен свой `worktree`: без него она работает в основном каталоге проекта, а не в своём worktree.

Тело общей роли попадает в инструкцию дословно, вместе с заполнителями `<…>`. Тонкий файл не вычёркивает строки общей роли, а дописывает уточнения: значения заполнителей и правила, которые в проекте другие.

## Как взять роль в свой проект

1. Подключите проект, если `agents/` ещё нет:

   ```bash
   cd <проект>
   team init
   ```

   `team init` создаёт:

   - `agents/team.yaml`;
   - `roles/manager.md` — тонкий файл с `extends: manager` и комментарием на месте уточнений проекта;
   - `roles/executor.md` — заготовку собственной роли-исполнителя со `status: draft`;
   - шаблон выдачи задачи `templates/task-assignment.md`. На него ссылается менеджер библиотеки, а в библиотеке шаблонов нет, поэтому не удаляйте его.

   Общие правила `shared/` заготовка не кладёт: файлы из `includes` общих ролей `team` находит в библиотеке.

2. Для каждой нужной роли заведите тонкий файл командой `team role new`:

   ```bash
   team role new developer --extends developer --start on_demand
   team role new reviewer --extends reviewer --start on_demand
   ```

   Команда создаёт `agents/roles/<роль>.md` с `extends`, `zone: []` и HTML-комментарием на месте уточнений и дописывает роль в `roles` файла `team.yaml`. Если у общей роли есть worktree, тонкий файл получает свой `worktree: {dir: <роль>, branch: team/<роль>}`. Без `--start` роль записывается со `start: manual`. Название, `kind` и `includes` роль получает от общей роли.

   Тонкий файл можно написать и руками; имя файла должно совпадать с полем `role:`, а роль нужно вписать в `team.yaml` (шаг 4):

   ```markdown
   ---
   role: reviewer
   extends: reviewer
   ---
   Команда тестов: <команда тестов>.
   ```

   Заготовку `executor.md` удалите вместе с её строкой в `team.yaml` или доработайте как собственную роль.

3. Замените HTML-комментарий в теле каждого тонкого файла уточнениями проекта: значениями заполнителей (таблица ниже) и правилами, которые в проекте другие. Если уточнять нечего, удалите комментарий: при пустом теле заголовка «Уточнения проекта» в инструкции нет. Во frontmatter впишите `zone` ролей, которые правят файлы, и `allow`, если нужны инструменты сверх общей роли.

4. Проверьте список ролей в `agents/team.yaml` (роли, заведённые `team role new`, уже вписаны) и задайте команду тестов. Значения `start` описаны в [`docs/SPEC.md`](../docs/SPEC.md).

   ```yaml
   test_command: <команда тестов>
   manager: manager
   roles:
     - role: manager
       start: manual
     - role: developer
       start: on_demand
     - role: reviewer
       start: on_demand
   ```

5. Проверьте описание:

   ```bash
   team check
   ```

   Команда разбирает frontmatter каждой роли, находит общую роль из `extends`, собирает инструкцию с `includes` и сверяет worktree и зоны между ролями. Итог — строка `роли: …; ошибок N, предупреждений M`. Поднимать команду (`team up`) можно, когда ошибок 0.

   - Ошибка в правиле `запуск <роль>` значит, что неверно поле запуска: имя в `mcp` не найдено ни в `mcp_servers`, ни в `~/.claude.json`, ни в `.mcp.json`, или неверна форма `plugins`, `env`, `context`. Предупреждение о пустом `mcp` значит, что роль с правилом про трекер осталась без сервера трекера.
   - Ошибка про `extends` значит, что общей роли с таким именем нет в библиотеке, общая роль сама наследует или имя записано путём (`../x`, `a/b`). Список общих ролей печатает `team roles --library`.
   - Предупреждение «файл назван как общая роль библиотеки, но extends не задан» значит, что в проекте лежит копия общей роли. Замените её тонким файлом или задайте наследование командой `team role set <роль> --extends <общая роль>`; тело файла команда не трогает, поэтому текст копии, повторяющий общую роль, из тела удалите.

## Что указать в уточнениях

Заполнители стоят в теле общих ролей и в общих правилах. Тонкий файл их не заменяет, а называет значения в своём теле. Найти заполнители можно поиском `<` по файлу общей роли в `roles/` и по файлам её `includes` в `roles/shared/`.

| Заполнитель или поле           | Где стоит                                    | Что указать в тонком файле                                                                                        |
|--------------------------------|----------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| `<трекер>`                     | `manager.md`, `shared/tracker-cycle.md`      | В теле: название трекера и проекта в нём                                                                          |
| `<команда тестов>`             | роли, которые запускают проверку             | В теле: команда полного прогона тестов, та же, что `test_command` в `team.yaml`                                   |
| `zone`                         | frontmatter                                  | Каталоги и файлы, которые правит только эта роль; инструмент вносит их в инструкцию разделом «Зона»                |
| `worktree`                     | frontmatter                                  | `{dir, branch}` у роли, которая правит файлы; из общей роли не наследуется                                         |
| `allow`                        | frontmatter                                  | Инструменты сверх списка общей роли: MCP трекера, линтер, проверка типов. Добавляются к `allow` общей роли        |
| `tracker_zone`                 | frontmatter                                  | Метка зоны роли в трекере; инструмент вносит её в раздел «Зона» инструкции                                         |
| `<команда резервной копии>`    | `shared/data-reversibility.md`               | В теле роли, которая подключает это правило: команда, которая делает копию данных и проверяет её целостность      |
| `<что улучшаем…>`, `<период>`  | `optimizer.md`                               | В теле: метрика роли и минимальный период между сменами настроек режима                                           |

Заполнитель в общем правиле можно закрыть и по-другому: положить в `agents/shared/` файл проекта с тем же именем и уже вписанным значением. Он заменит файл библиотеки для всех ролей проекта.

Проект без трекера убирает общее правило работы с трекером из `includes` полем `exclude` в тонком файле каждой роли, которая его подключает (менеджер, `developer`, `writer`, `data`, `optimizer`):

```yaml
exclude:
  includes: [tracker-cycle.md]
```

`exclude` убирает только элементы общей роли; так же убираются лишние `allow` и `add_dirs`. Если исключаемого элемента в общей роли нет, `team check` предупреждает об этом.

Зону пишут один раз, во frontmatter. Поле `zone` нужно `team check`: по нему он находит файлы, записанные за двумя ролями сразу. Инструмент вносит `zone` и `tracker_zone` в инструкцию разделом «## Зона» после уточнений проекта, поэтому строку «Твоя зона» в теле не пишут. У исполнителя без `zone` раздел говорит, что файлы называет задача менеджера.
