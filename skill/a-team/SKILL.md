# a-team

Ведёт пользователя через работу с командой агентов проекта: подключение, подъём в tmux, передачу дел менеджеру и остановку. Исполнитель всех действий — CLI `team` из репозитория agent-team.

**Каталог инструмента** — клон репозитория agent-team, в котором лежит этот скилл (`<клон>/skill/a-team/`; в `~/.claude/skills/` скилл подключён симлинком). В клоне лежат формат ролей и правила наследования (`docs/SPEC.md`, разделы «Роль» и «Наследование общей роли»), библиотека общих ролей (`roles/`, каталог и шаги подключения — `roles/README.md`) и описание команд (`docs/agent-guide.md`, на английском).

## Аргумент

`/a-team [init | up | status | handoff <роль> | down [роль]]`. Без аргумента сценарий выбирается по состоянию (шаг 1).

## Процесс

### 1. Состояние

- Найти каталог инструмента: перейти в базовый каталог этого скилла (Claude Code называет его при загрузке скилла строкой «Base directory for this skill»; если такой строки нет — `~/.claude/skills/a-team`) и подняться на два уровня по настоящему пути, а не по симлинку:

  ```bash
  cd "<базовый каталог скилла>" && cd "$(pwd -P)/../.." && pwd
  ```

  Готово, когда в найденном каталоге есть `pyproject.toml` с `name = "agent-team"`. Дальше этот путь называется `<клон>`.
- Проверить, что `tmux` и `claude` есть в `PATH`. Без них не продолжать: сказать пользователю, чего не хватает.
- Проверить, что `team` есть в `PATH`. Если нет и есть `uv`, во всех шагах ниже вместо `team` вызывать `uv run --project <клон> team` из каталога проекта. Если нет и `uv`, не продолжать: сказать пользователю, что нужен `uv`.
- Сам инструмент глобально не устанавливать: это решение пользователя. Если `team` нет в `PATH`, в выходе назвать команду установки `uv tool install --editable <клон>`.
- Корень проекта: `git rev-parse --show-toplevel`.
- `agents/team.yaml` есть → `team check` и `team status`.
- Выбор сценария без аргумента:
  - `agents/` нет → «Подключить проект»;
  - tmux-сессии нет → «Поднять команду»;
  - сессия есть → «Состояние».

Готово, когда сценарий выбран и сказан пользователю одной строкой.

### 2. Подключить проект (init)

1. Изучить проект: `CLAUDE.md`, `README`, структуру каталогов, команду тестов, трекер задач (есть ли строка подключения трекера в `CLAUDE.md`). Правила безопасности и запреты брать только из документов проекта, не придумывать.
2. Предложить пользователю состав: менеджер и один–три исполнителя. Подходящие общие роли брать из таблицы ролей в `<клон>/roles/README.md`: там же сказано, когда какая нужна (`team roles --library` работает только после `team init`). У каждого исполнителя своя зона файлов, зоны не пересекаются, общие файлы (точка входа CLI, миграции) отданы одной роли. Показать таблицей «роль — за что отвечает — зона — модель» и получить согласие одним вопросом.

   **СТОП: без согласия на состав не запускать `team init` и не писать файлы ролей.** `team init` создаёт `agents/` в проекте, поэтому до согласия в проекте ничего не меняется.
3. `team init` в корне проекта. Готово, когда `agents/team.yaml` создан, а `team` перечислил созданные файлы.
4. Записать роли по формату из `<клон>/docs/SPEC.md`, разделы «Роль» и «Наследование общей роли». Общую роль не копировать, а наследовать тонким файлом с `extends`:
   1. Менеджер: `team init` уже положил тонкий `agents/roles/manager.md` с `extends: manager`. Заменить HTML-комментарий в его теле уточнениями проекта: трекер, команда тестов. Если трекера нет, так и написать: «Трекера нет, задачи ставит пользователь в разговоре с тобой».
   2. Каждую остальную роль из согласованного состава завести командой `team role new <роль> --extends <общая роль> --start on_demand`. `<роль>` — имя роли проекта, оно же имя файла; оно может отличаться от общей роли: две роли с одной общей называются по зонам, например `api-dev` и `reports-dev` с `--extends developer`. Команда создаёт `agents/roles/<роль>.md`, строит `worktree: {dir: <роль>, branch: team/<роль>}` по имени роли проекта (если у общей роли есть worktree) и дописывает строку `- {role: <роль>, start: …}` в `roles` файла `agents/team.yaml`. Без `--start` она запишет `start: manual`. Готово, когда команда напечатала JSON роли; ошибка — код 1 и текст в stderr, файлы не меняются.
   3. В каждом тонком файле заменить HTML-комментарий в теле уточнениями проекта, а во frontmatter вписать `zone`.

   Пример готового тонкого файла (единственная роль на основе `developer`; при двух — имена по зонам, как в пункте 2):

   ```markdown
   ---
   role: developer
   extends: developer
   worktree: {dir: developer, branch: team/developer}
   zone: [api/]
   ---
   Команда тестов: `pytest`.
   ```

   Правила:
   - тело общей роли входит в инструкцию дословно, с заполнителями `<…>`. В тело тонкого файла вписать их значения: зону, команду тестов, трекер. Какие заполнители у какой роли — таблица «Что указать в уточнениях» в `<клон>/roles/README.md`. Если уточнять нечего, удалить комментарий: пустое тело допустимо;
   - `zone` не наследуется: у роли, которая правит код, вписать `zone` в тонкий файл; инструмент сам внесёт её в инструкцию разделом «Зона», в теле зону не повторять. `worktree` тоже не наследуется; `team role new` добавляет свой, если он есть у общей роли — проверить, что он в файле;
   - файлы `includes` общих ролей в `agents/shared/` не копировать: `team` берёт их из библиотеки, а файл проекта с тем же именем заменяет библиотечный. Класть такой файл — только чтобы намеренно заменить общее правило проекта своим текстом;
   - заготовку `agents/roles/executor.md` от `team init` удалить вместе с её строкой в `team.yaml`, если её место заняли общие роли;
   - модель задана общей ролью; `--model` передавать, только если пользователь хочет другую;
   - `allow` — только то, что нужно сверх общей роли: MCP трекера, `Bash(gh *)` менеджеру. Список складывается со списком общей роли. `--dangerously-skip-permissions` и `bypassPermissions` не предлагать;
   - собственную роль, без `extends`, заводить (`team role new <роль> --title <…>`), только если подходящей общей роли нет. Значение `description` всегда в кавычках, потому что `: ` внутри ломает разбор;
   - трекера нет → после `team role new` посмотреть `includes` ролей в `team roles --json`. В тонкий файл каждой роли, у которой там есть `tracker-cycle.md` (в библиотеке это менеджер, `developer`, `writer`, `data`, `optimizer`), вписать `exclude: {includes: [tracker-cycle.md]}`: правило работы с трекером ей не подключается. В тело такой роли вписать вместо трекера: «Трекера нет: задачи и их статус ведёт менеджер, задачу получаешь и отчитываешься сообщением». Текст для менеджера — в пункте 1;
   - правило, общее для нескольких ролей проекта, — один файл в `agents/shared/`, роли подключают его через `includes`. Файл с именем общего правила библиотеки заменяет его.
5. Заполнить `team.yaml`: `test_command`, `layout` (по умолчанию `panes`). `worktree_root` оставить как записал `team init`: `../<проект>-wt`, где `<проект>` — значение `project` в `team.yaml`; это каталог рядом с репозиторием. Путь считается от корня проекта (`repo` в `team.yaml`). Каталог worktree должен лежать вне репозитория: worktree внутри него `git status` основного репозитория показывает неотслеживаемым каталогом. Другое значение — только если пользователь назвал другой каталог, и тоже вне репозитория. Проверить `start` в строках ролей списка `roles` в `team.yaml` (во frontmatter файла роли `start` не пишется): менеджер — `manual`, исполнители — `on_demand`.
6. Необязательно, по желанию пользователя: настроить лёгкий старт и автоостановку. Спрашивать, только если пользователь сам заговорил о стоимости, размере контекста или лишних MCP и плагинах. Иначе пропустить: без этих полей роли стартуют как раньше, а автоостановка работает с порогом 15 минут.
   - Лёгкий старт: блок `defaults` и `mcp_servers` в `agents/team.yaml`, поля `mcp`, `plugins`, `chrome` в файле роли. Формат и правила слоёв — `<клон>/docs/SPEC.md`, раздел «Запуск роли: MCP, плагины, настройки». Роли, которая работает с трекером через MCP, нужен сервер трекера в `mcp`; пустой `mcp: []` ломает ей работу, и `team check` предупреждает об этом.
   - Автоостановка (включена по умолчанию): `team set idle_stop_minutes <минуты>` задаёт порог простоя в минутах для ролей со `start: on_demand` (без ключа порог 15 минут; `off` выключает автоостановку и пишется в `team.yaml` строкой `idle_stop_minutes: off`). Останавливает их `team reap` (раздел «Автоостановка» в SPEC), который вызывает десктоп-приложение AgentTeam раз в минуту для каждого проекта с живой сессией команды (открыт он в приложении или нет) или пользователь вручную. Порог можно сменить и в приложении: ячейка «автоостановка» на экране «Роли» вызывает ту же команду `team set`. Без вызова `reap` порог ничего не делает — так и сказать пользователю. Порог по умолчанию нужен затем, что простаивающие агенты «по требованию» держат контекст, и Claude Code сжимает его без хода, тратя лимит.
7. `team check`. Готово, когда ошибок 0. Предупреждения показать пользователю. Предупреждение «файл назван как общая роль библиотеки, но extends не задан» значит, что в проекте лежит копия общей роли. Задать наследование командой `team role set <роль> --extends <общая роль>`; тело файла команда не трогает, поэтому из тела удалить текст, повторяющий общую роль, и оставить только уточнения проекта.
8. Добавить `.team/` в `.gitignore` проекта.
9. Проверить, есть ли в репозитории коммит: `git rev-parse --verify HEAD`. Задать пользователю один вопрос о коммите; без его слова не коммитить:
   - коммит есть — спросить, коммитить ли `agents/` и `.gitignore`;
   - коммитов нет (команда завершилась ошибкой; `team check` на шаге 7 предупреждает о том же: «нет коммитов: роли с worktree не поднимутся») — сказать, что до подъёма команды нужен первый коммит. Причина: в репозитории без коммитов `team` не поднимает роли с worktree — `team spawn` такой роли завершается ошибкой, а `team up` отказывает целиком, если такая роль стоит `always`. Менеджер поднимется, но исполнителей запустить не сможет. Показать `git status --short` и предложить первый коммит из файлов проекта, `agents/` и `.gitignore`. Файлы с секретами (`.env`, ключи) в список не включать и назвать их пользователю отдельно. Коммит делает скилл, после согласия, ровно с теми файлами, которые пользователь одобрил.

Затем перейти к шагу 3, если пользователь хочет поднять команду сейчас.

### 3. Поднять команду (up)

1. `team check` — ошибок 0.
   **СТОП, если `git rev-parse --verify HEAD` завершается ошибкой:** коммитов нет, команду не поднимать. Без коммита `team` не запускает роли с worktree (шаг 2.9), и команда из одного менеджера работу не сдвинет. Сказать пользователю, что нужен первый коммит.
2. `team up`, через 10 секунд `team peek manager 30`.
   - Видно «Do you trust this folder» / «Quick safety check» → не отвечать за человека. Сказать пользователю: `team attach`, выбрать «Yes, I trust this folder», `Ctrl-b d`. Когда пользователь ответит, повторить `team peek manager 30`.
   - Готово, когда в выводе панели есть строка модели и пустое поле ввода, а `team status` показывает менеджера «работает».
3. Передать дела менеджеру. Это первое сообщение ему, поэтому без него он начинает с чистого контекста. Собрать из этого разговора и трекера:
   - задачи в работе и их статус;
   - ветки и worktree с незаконченной работой;
   - принятые решения, которых нет в файлах;
   - что ждёт решения пользователя.

   Отправить через `SendMessage` на адрес из `team addr manager` (вида `uds:…`), а не по имени: имена сессий бывают неуникальны. Если адреса нет или доставка не прошла — сказать пользователю; `team send manager --paste` только с его согласия, потому что вставка выглядит как ввод пользователя. Готово, когда в `team peek manager` видно, что сообщение принято в работу.
4. С этого момента текущая сессия ролями не управляет: задачи раздаёт только менеджер в tmux, иначе у команды два источника указаний.
5. Сказать пользователю, как подключиться:
   - `team attach`;
   - говорить только с менеджером;
   - стрелка с префиксом `Ctrl-b` — соседняя панель, `Ctrl-b z` — развернуть панель, `Ctrl-b d` — отключиться, не останавливая агентов.

### 4. Состояние (status)

`team status` и `team peek` по каждой работающей роли (20 строк). Кратко пересказать:
- кто жив;
- кто ждёт ответа человека: в столбце «состояние» `ждёт: доверие` (вопрос о доверии к папке) или `ждёт ответа` (запрос права, вопрос роли). Назвать роль и сказать пользователю: ответ даёт он сам через `team attach <агент>`; за него не отвечать;
- у кого в столбце «состояние» `! в фоне`, `! чужой процесс` или `! без роли`: в панели не сессия роли. Сказать пользователю команду из строки под таблицей (`team restart <агент>`) и не выполнять её без его слова;
- у кого в столбце `ctx` пометка `сброс` или `сброс*`: контекст выше порога, пора начинать с чистого. Сброс решает менеджер на границе задач; пользователю назвать, у кого и какого размера (`сброс*` — сброс пока заблокирован, причина напечатана под таблицей);
- кто молчит дольше часа (столбец «тихо»).

Ничего не отправлять ролям.

### 5. Передача и перезапуск роли (handoff)

Передача здесь — файл, в который роль записывает состояние своей работы перед пересозданием сессии. Скилл делает этот шаг только по прямой команде пользователя `/a-team handoff <роль>` или по шагу 6. Это исключение из правила шага 3.4: скилл запрашивает передачу и перезапускает сессию, но задач роли не выдаёт.

1. `team handoff <роль>`. Если команда отказала из-за грязного worktree, сказать пользователю, какие файлы она назвала, и спросить: роль коммитит или откладывает правки, либо нужен `--force`. `--force` без слова пользователя не использовать: после сброса несохранённое теряется из виду. Если отказа нет, команда создаёт файл передачи в `.team/handoffs/` и печатает адрес роли (тот же, что `team addr <роль>`) и текст запроса с путём к файлу. Отправить этот текст `SendMessage` на напечатанный адрес. Если адреса нет или доставка не прошла — сказать пользователю; `team handoff <роль> --paste` только с его согласия, потому что вставка выглядит как ввод пользователя. Повторный `team handoff` той же роли, пока её последняя передача пуста, пишет в тот же файл, а не создаёт новый.
2. Через минуту `team handoffs --json`. Найти первую в списке запись с `agent` этой роли (`<роль>#1`): список идёт от новых к старым. Готово, когда в её `sections` заполнены разделы. Готовность смотреть по файлу, а не по выводу панели. Пока разделы пусты, проверять раз в минуту. Если через 10 минут они всё ещё пусты, посмотреть `team peek <роль> 30`: роль могла встать на вопросе о правах или доверии к папке. Не отвечать за человека, сказать пользователю.
3. Если пользователь просил перезапуск — `team restart <роль>` (продолжить ту же сессию) или `team restart <роль> --fresh` (новая сессия). Новая сессия файл передачи сама не читает: путь к нему ей передаёт менеджер. Поэтому после `--fresh` отправить менеджеру `SendMessage` на адрес из `team addr manager`: роль перезапущена, адрес новой сессии — `<адрес>`, передача — `<путь к файлу>`. Адрес и путь печатает сам `team restart --fresh` строками «адрес для SendMessage» и «последняя передача»; если адрес ещё не зарегистрирован, взять его позже из `team addr <роль>`.

### 6. Остановка (down)

- Для каждой роли с незаконченной работой (по `peek`: правки без коммита, задача в процессе) — сначала шаг 5.
- Затем `team down <роль>` или `team down` для всей команды.
- Готово, когда `team status` показывает «не запущена».

## Общие правила

- Сообщения ролям — только `SendMessage` на адрес из `team addr <роль>`. `team send --paste` — запасной путь: перед ним `team peek`, и если в поле ввода уже есть текст, не вставлять.
- Не нажимать за человека ответы на вопросы о доверии и правах.
- Роли закрывает только менеджер или пользователь. Скилл закрывает их только по команде `down`.

## Выход

Пользователю одним сообщением:
- что сделано: сценарий, команды, итог `team check` и `team status`;
- как подключиться;
- что ждёт его ответа.

Проверка скилла — `scenarios.md` рядом; читать, когда скилл меняется.
